# @debutify/liquidjs

Debutify's fork of [LiquidJS](https://github.com/harttle/liquidjs) for rendering Shopify themes outside Shopify. With default options it is LiquidJS (see `NOTICE.md`). Install with `npm install @debutify/liquidjs`. It runs on Node.js 24 or newer; the browser bundles of the root entry are unchanged. Besides the root entry it has two Node.js entries: `@debutify/liquidjs/shopify`, which renders Shopify themes, and `@debutify/liquidjs/storefront`, which serves a whole store as a function from a `Request` to a `Response`.

## Options added by this fork

| Option | Default | Effect |
| --- | --- | --- |
| `numberSemantics` | `'js'` | `'ruby'` keeps whole numbers and decimals apart as Shopify Liquid does (`{{ 10 \| divided_by: 4 }}` is `2`, `{{ 2.0 }}` prints `2.0`, `{{ 2.0 \| json }}` is `2.0` where the runtime has `JSON.rawJSON`, decimal arithmetic is exact). |
| `forloopParentloop` | `false` | `true` gives `forloop` a `parentloop`, the `forloop` of the `for` loop it is nested in (nil at the outermost loop and in a `render`ed partial, which has a context of its own), as Ruby Liquid does; a loop in an `include` sees the loop around the `include`. With `false` `forloop.parentloop` is undefined, as in upstream LiquidJS. The Shopify preset (`createShopifyLiquid`) sets it to `true`. |
| `rawTags` | `['raw']` | Tags whose bodies are never parsed; register a `RawBodyTag` subclass for each new name. A listed `comment` nests. The list replaces the default, so include `raw` to keep `{% raw %}` raw. |
| `inlineErrors` | `false` | Write render errors inline (`Liquid error (line 1): …`) and keep rendering; collect them with `render(tpl, scope, { errors })`. |
| `topLevelSize` | `true` | `false` makes an undefined top-level `size` print nothing, as Ruby Liquid does, instead of the number of keys in the render's globals as upstream LiquidJS does; a `size` that a scope or the globals define, and the `size` of a value (`list.size`), are not affected. The Shopify preset sets it to `false`. |
| `bugCompatibleWhitespaceTrimming` | `false` | `true` trims as Ruby Liquid's `bug_compatible_whitespace_trimming` parse option, which Shopify's storefront parses themes with: when `{%-` or `{{-` strips the text before it to nothing, the text keeps its first character, so `{{ a }}\n  {%- if b %}` keeps the newline. The Shopify preset sets it to `true`. |

```js
const { Liquid } = require('@debutify/liquidjs')
const liquid = new Liquid({ numberSemantics: 'ruby', rawTags: ['raw', 'comment'], inlineErrors: true })

const errors = []
liquid.parseAndRender('{{ 10 | divided_by: 4 }} {{ 2.0 }} {{ 1 | divided_by: 0 }}', {}, { errors }).then(html => {
  console.log(html)          // 2 2.0 Liquid error (line 1): divided by 0
  console.log(errors.length) // 1
})
```

Details that do not fit the table:

- With `numberSemantics: 'ruby'`, decimal values that reach API callers (`evalValue`, `evalValueSync`, values written by `assign`) are `LiquidFloat` objects: read `.value`, or use `Number(x)`.
- A `rawTags` list replaces the default `['raw']` instead of adding to it. Without `raw` in it, the body of `{% raw %}` is parsed as Liquid, so `rawTags: ['comment']` makes `{% raw %}{{ x {% endraw %}` a tokenization error.
- Setting `rawTags` explicitly, even to the default list, lets an end tag carry a whitespace-control marker in the forms `{%- endraw -%}`, `{% endraw-%}` and `{%- endraw %}`. Under the default list those three stay unclosed, as in upstream LiquidJS, while `{% endraw -%}` closes either way.
- With `inlineErrors`, an error in a tag that prints nothing (`assign`, `capture`, a block with a blank body) is recorded in `errors` and not written.
- With `inlineErrors`, an undefined variable is recorded and not written, but it is an error only under `strictVariables`; by default nothing is recorded.
- With `inlineErrors`, an undefined filter is recorded and not written only when it is met while rendering, for example inside a grouped expression (`groupedExpressions`). Under `strictFilters` a misspelt filter in an ordinary tag is a parse error and still throws, as in upstream LiquidJS, and without `strictFilters` it is not an error at all.
- With `inlineErrors`, a syntax error met while rendering, such as in a partial parsed at render time, is written as `Liquid syntax error (<file> line <n>): <message>`. A syntax error in the template you pass to `parse` still throws, and so does a limit error (`memoryLimit`, `renderLimit`, `parseLimit`). A limit hit while rendering arrives wrapped in a `RenderError`, so test what you catch with `isLimitError(err)`, which looks through `originalError`; `LimitError.is(err)` is false for the wrapper.
- With `topLevelSize: false`, `{{ size }}` prints nothing, `{% if size %}` is false and `{{ size | default: 'M' }}` prints `M` when nothing defines `size`. Under `strictVariables` an undefined `size` throws like any other undefined variable.
- With `bugCompatibleWhitespaceTrimming: true`, a text that a `-%}` or `-}}` already stripped to nothing keeps nothing, a text with anything but whitespace in it is stripped as before, and the body of a raw tag is never trimmed.

All six defaults are upstream LiquidJS's behaviour, so none of these options changes anything until you opt in.

One behaviour differs from upstream without an opt-in: the `slice` filter charges `memoryLimit` for the length of the array or string it returns, where upstream LiquidJS 10.30.0 charges the length it was asked for, so `{{ list | slice: 0, 1000 }}` over a short array no longer hits a low `memoryLimit`. It only matters once you set `memoryLimit`, which is unlimited by default; the Shopify preset sets it.

## Upgrading from 1.3

1.4.0 is a minor release: it adds optional store-data fields, one export (`previewSampleData`) and one storefront route, and everything 1.3.0 exports is still exported with the same signatures. Every new field is optional and a store that leaves it out behaves as under 1.3.0, except where a bullet below says what changed; the one exception on the root entry (`@debutify/liquidjs`) is the `for` fix. This is every change a 1.3.0 caller can see.

**Engine**

- **`offset: continue` starts where the previous loop ended, also for the first loop.** https://shopify.dev/docs/api/liquid/tags/for documents `offset: continue` as starting the loop where the previous `for` over the same collection stopped; with no previous loop that is the start, as in Ruby Liquid, where the offset is `offsets[name].to_i`. 1.3.0 (and upstream LiquidJS) read an empty object as the offset when no loop had run before, which is `NaN`: the loop started at 0 and stored a string, so every later `offset: continue` over that collection started at 0 as well, and inside an outer loop that repeated every round. This is a fix on the root entry and needs no option. To do: nothing; the first loop is unchanged and the loops after it now continue from it.

**Objects**

- **`product.gift_card?` and `line_item.gift_card` follow the data.** https://shopify.dev/docs/api/liquid/objects/product#product-gift_card? and https://shopify.dev/docs/api/liquid/objects/line_item document them as true for a gift card. 1.3.0 had no way to say so and both were always false, so the gift card recipient form and the shipping notes a theme branches on never showed. `ProductData.gift_card` (`boolean`, false when omitted) sets it, and a cart line of that product has `gift_card` true. A gift card is left out of `recommendations`, as before. To do: set `gift_card: true` on the product and `requires_shipping: false` on its variants.
- **A variant has `quantity_price_breaks_configured?` and takes its `quantity_rule` from the data.** https://shopify.dev/docs/api/liquid/objects/variant documents `quantity_price_breaks_configured?` as whether the variant has any quantity price breaks; 1.3.0 had it on the product only, so a variant read nil. It is now true when `VariantData.quantity_price_breaks` holds at least one break. https://shopify.dev/docs/api/liquid/objects/quantity_rule documents the rule: 1.3.0 gave every variant the default rule (`min` 1, no `max`, `increment` 1), so volume pricing and minimum or step quantities could not be previewed. `VariantData.quantity_rule` (`{ min?, max?, increment? }`; `min` and `increment` default to 1 and `max` to none) sets it, and a variant that leaves it out still has the default rule.
- **A country has `popular?`.** https://shopify.dev/docs/api/liquid/objects/country documents it; 1.3.0 read nil, so a country selector that lists popular countries first listed none. It is on `localization.country` and on each of `localization.available_countries`, from the new optional `popular` of the entries of `MarketData.countries` (`{ iso_code, name, popular? }`), false when omitted.
- **`recommendations` with `intent=complementary` lists the products a merchant set up.** https://shopify.dev/docs/storefronts/themes/product-merchandising/recommendations/complementary-products says they are set up by hand in the admin; 1.3.0 modelled no such setup, so the intent always held no products. `ProductData.complementary_products` (the handles, in the merchant's order; none when omitted) sets them, and they are left out the same way as related products: the product itself, unavailable products, products with a price of 0, gift cards and products in the cart. A product with none set up still has none, as on the parity store (fixture `probe-recommendations-complementary`). This also reaches `recommendationsJson` and `/recommendations/products.json?intent=complementary`.

**Pages**

- **A `template--<name>__<key>` section id renders in the template it names.** https://shopify.dev/docs/api/ajax/section-rendering says a `section_id` "can be used to render a section in the context of any page", and https://shopify.dev/docs/api/ajax/reference/product-recommendations is the request a product page makes with `section_id=template--product__<key>`. That request is read as the `index` template, so 1.3.0 looked the section up there and `renderSection` and `/recommendations/products` answered 404 (the section was not found). `renderSection` now finds the section in the other JSON template of the theme and renders it with that template's settings on the requested page's objects, so a product page's recommendations section loads. The template is found by its id (its name with every character but letters, digits, `_` and `-` as `-`, so `product.probe` is `product-probe`) and the longest matching name wins. An id that names no template of the theme, or no section in it, is not found, as before. To do: nothing.

**Storefront**

- **A sandboxed page keeps its `localStorage` and `sessionStorage` across page loads.** 1.3.0 gave each page empty in-memory storages, so what a theme remembers across pages (recently viewed products, a products-per-row choice, scroll restore) was gone on the next page. A sandboxed page has an opaque origin and no storage of its own (https://html.spec.whatwg.org/multipage/browsers.html#sandboxed-origin-browsing-context-flag), and `window.name` would be readable by any site the frame is sent to, so the storefront keeps both storages in the visitor's state beside the cart (`VisitorState.storage`, `{ local, session }`, each a map of text to text). The page carries the visitor's storage as JSON in the client script, escaped like the base path, so the storages are full before any script of the page runs. A change is sent back with `POST <base path>/storefront-storage` (both storages whole, 100 ms after the last change and at once when the page is hidden, with `keepalive`, through the page's own `fetch` as it was before the script wrapped it, so a theme that patches `fetch` never sees it), and the answer is 204. The route runs one visitor at a time like the cart routes, is refused with 413 past `limits.body`, keeps at most 500 names per storage and only text values, and answers 404 on a page that is not sandboxed. The visitor is the base path's token, so another visitor or another build starts empty. The storages keep the same API for theme scripts; only what a page starts with changes.
- **How to use it, and how to leave it out.** With `sandbox: true` it is on and needs nothing from the host except that `POST <base path>/storefront-storage` reaches `handle` (a host that hands only `GET` to it loses the saves, silently, and the page keeps working with in-memory storages). A custom `CartStore` must give back the `storage` of the state it was given: a state whose `storage` is not two maps of text to text is repaired like any other invalid state (reported to `onReport` as an `error`, the cart emptied), and one that drops the field gives every page empty storages. A host that builds its own pages calls `storefrontClientScript({ basePath, storage })` with the visitor's `{ local, session }` to start the page with them; calling it as before, `storefrontClientScript({ basePath })`, gives the 1.3.0 script, with in-memory storages and no saves. There is no option on `createStorefront` that switches the persistence off: a page that is not sandboxed has real storage and no use for it, and for a sandboxed page the storages are the visitor's, saved beside the cart.

**Sample data**

- **`previewSampleData` is the sample store for previewing a theme.** It is `storefrontSampleData` plus four products that the mock.shop catalogue cannot show: `gift-card` (`gift_card` true, three denominations, no shipping), `wholesale-tee` (quantity price breaks at 10, 25 and 50 and a quantity rule of 5 to 200 in steps of 5), `scented-candle` (the `shopify.disclosure` metafield with two disclosure metaobjects, one for `US-CA`) and `video-tote` (a hosted video and a YouTube video beside its image). They sit in no collection, so `/collections/all`, search and their own pages list them. It is a separate export because the parity scenarios compare `storefrontSampleData` with recordings of the parity store, and four more products would change their product lists, search results and counts; `sampleStoreData` and `storefrontSampleData` are unchanged. It is frozen, like the other two. To do: nothing; pass `previewSampleData` as `data` where you passed `storefrontSampleData` to preview those features.

**Types**

- **New optional store data fields.** `ProductData.gift_card`, `ProductData.complementary_products`, `VariantData.quantity_rule` and `popular` on the entries of `MarketData.countries`, and `VisitorState.storage` (`{ local: Record<string, string>, session: Record<string, string> }`) on the visitor state; `storefrontClientScript` takes an optional `storage` of the same shape (`{ local, session }`). Nothing a 1.3.0 caller passes is rejected.

## Upgrading from 1.2

1.3.0 is a minor release: it adds options, routes and Shopify behaviour, and everything 1.2.0 exports is still exported, and the root entry (`@debutify/liquidjs`) behaves as 1.2.0 unless you opt into the new `forloopParentloop` option. That option is the only change to the root entry; everything else below is in `@debutify/liquidjs/shopify` and `@debutify/liquidjs/storefront`, and this is every change a 1.2.0 caller can see.

**Engine**

- **`forloop.parentloop` is the enclosing loop's `forloop`.** https://shopify.dev/docs/api/liquid/objects/forloop documents it, nil outside a nested loop; upstream LiquidJS and 1.2.0 had none, so our theme's slideshow marked no thumbnail active. As in Ruby Liquid, a loop in an `include` sees the loop around the `include`, and a loop in a `render` does not. It is on through the Shopify layer (`createShopifyLiquid` sets `forloopParentloop: true`) and opt-in on the root entry (`@debutify/liquidjs`): with the option off, which is the default, `forloop.parentloop` reads nil, as in upstream LiquidJS and 1.2.0. `ForloopDrop` takes the parent loop as an optional fourth argument, and has no `parentloop` without it. To do: nothing for a Shopify theme; a root-entry caller that wants it sets `forloopParentloop: true`.

**Filters**

- **New filters.** `md5`, `preload_tag`, `inline_asset_content`, `structured_data`, `standard_event_data` and `money_amount` are `exact`, matched against the parity store's recordings of Horizon and Dawn; `applicable_disclosures`, `line_items_for`, `login_button`, `metafield_tag`, `model_viewer_tag` and `unit_price_with_measurement` are `approx`, built from their shopify.dev pages. In 1.2.0 they printed nothing and were reported as stubs. `inline_asset_content` reads the theme's own `assets/` files (an SVG, JS or CSS file under 15 KB, an overlay's own file before its base's), never the network.
- **`powered_by_link` prints Shopify's link**, `<a target="_blank" rel="nofollow" href="https://www.shopify.com?utm_campaign=poweredby&amp;utm_medium=shopify&amp;utm_source=onlinestore">Powered by Shopify</a>`, with French words on a French page, where 1.2.0 printed nothing. A caller that must not show the link removes `powered_by_link` from its theme.
- **`default` returns a drop as itself.** A drop that is not empty comes back as the drop, as Ruby's filter returns its input, where 1.2.0 handed on its plain value: `{% assign c = setting | default: other %}` keeps a drop's properties (a `color` object's `rgba`), so Horizon's button colours no longer print `rgb()`, and `image | default: other | image_url` keeps the image's size, so `image_tag` prints `height`. A drop that prints as an empty string, a drop whose `empty?` is true (a settings object with no settings) and a hash with no keys take the default, as in Ruby. The root entry's `default` is upstream LiquidJS's.
- **`image_tag` prints the parity store's order**: `src`, `alt`, `srcset`, `width`, `height`, `loading`, the focal-point `style`, then the named attributes as the template wrote them, `sizes` among them (1.2.0 printed `sizes` and `style` before `loading`). A `widths` list stops at the URL's width.
- **`image_tag` leaves out an `alt` that is nil.** `alt: nil` (and an unset variable) prints no `alt` attribute, where 1.2.0 printed `alt=""`; `alt: ''` still prints `alt=""`. The bare media a variant filter shows as a product's `featured_media` has a nil `alt` when it has no alt text of its own (an empty string, 1.2.0), so Horizon's product card, which passes `alt: media.alt`, prints no `alt` on the card of a product shown through its variant, as the parity store does. To do: nothing; pass `alt: ''` to print an empty one.
- **`image_tag` takes its size and `srcset` from the `image_url`.** `{{ image | image_url: width: 3840 | image_tag: widths: … }}` of an image 1024 wide prints `width="3840"`, the matching `height` and a candidate for every width up to 3840, as the parity store prints Horizon's collection cards; 1.2.0 cut all three to the image's own size. A width worked out from a `height` alone is held to the 5760 maximum, with the ratio kept. `ImageUrlDrop.params` holds the size the template asked for.
- **A name written twice prints once.** Every filter that writes named arguments as attributes prints a name written twice where it was first written, with its last value; 1.2.0 printed it twice.
- **A focal point prints as Ruby decimals**: `50.0% 50.0%`, where 1.2.0 printed `50% 50%`, in `focal_point` and in `image_tag`'s `style`; `1.9231% 9.7917%` is unchanged.
- **The colour filters return a colour object.** `color_darken`, `color_lighten`, `color_saturate`, `color_desaturate`, `color_modify` and `color_mix` return a `ColorDrop` that prints the text 1.2.0 returned and also answers `.red`, `.green`, `.blue` and the other fields of a colour. A caller that checks `typeof result === 'string'` reads `String(result)` instead. A `ColorDrop`, a `color` setting's included, writes its text through `json` (`"#334fb4"`). `size` of the result is 0, as for a `color` setting, where 1.2.0's string gave its length (7 for `#bfbfbf`).
- **`first` gives the first item of a drop that iterates.** Under `/shopify`, `{{ settings.color_schemes | first }}` prints the first scheme's id (Dawn's `color-scheme-1`), and a drop that iterates nothing gives nil; 1.2.0 printed nothing for any drop. `first` is now `approx` in `shopifyFilterRegistry()`, not `engine`. `last` and the root entry's `first` are unchanged.
- **`find_index`, `find` and `has` read strings as Ruby does.** Under `/shopify`, `{{ sizes | find_index: '56' }}` of `['012', '056']` is `1`: a string item answers the property when it contains it (`'056'['56']`), where 1.2.0 read `56` as a number and found nothing. A number reads the character at that place, as Ruby's `String#[]` does (`'abc'[1]` is `'b'`, `'056'[56]` is nil). Horizon's type scale uses it, and prints `--font-size--h1: clamp(3.0rem, …)` and `--font-size--h2: clamp(2.25rem, …)` where 1.2.0 printed `3.5rem` for both. The `nil` keyword as the value to match means no value, so `find: 'x', nil` takes the first item whose `x` is truthy. Hashes and drops are read as before. The three are now `approx` in `shopifyFilterRegistry()`, not `engine`; the root entry is unchanged.
- **`concat` keeps a drop as one item, and appends a drop that iterates.** Under `/shopify`, `product.featured_media | concat: other_media` starts the list with the media object, as Ruby Liquid does, where 1.2.0 started it with the text the media prints; a drop that iterates adds its items. A card's first slide in Horizon now has its media (`product-media-container--image`, `slide-id`). `concat` is `approx` under `/shopify`; the root entry is unchanged.
- **`placeholder_svg_tag` prints Shopify's outer element.** The `<svg>` carries the attributes, their order and the viewBox Shopify prints for the same name: `0 0 525.5 525.5` for `image`, `product-N` and `collection-N`, `0 0 1052 400` for `lifestyle-N`, `preserveAspectRatio="xMaxYMid slice" viewBox="0 0 1300 730" fill="none"` for `hero-apparel-N` and `preserveAspectRatio="xMidYMid slice" width="448" height="448" viewBox="0 0 448 448" fill="none"` for the other `*-apparel-N` names. The drawing inside stays Debutify's own, drawn to fit that viewBox (a `transform` on its `<path>`, and `fill="currentColor"` where the `<svg>` has `fill="none"`). 1.2.0 printed the `0 0 525.5 525.5` square for every name.

**Tags**

- **A page's `part.title` is its number.** `{% if part.title == paginate.current_page %}`, which Dawn 16.0.0 uses to mark the current page, now holds for the current page's part, as it does on the parity store (`aria-current="page"` on page 2 of a collection); 1.2.0 gave the part the text `"2"`, which never equals the number 2, so no page was marked. `{{ part.title }}` still prints `2`, and the gap's title is still `&hellip;`. A theme that compares a part's title with a string (`part.title == '2'`) no longer matches; compare with a number, or with `| plus: 0` as Horizon does. To do: nothing for Dawn, Horizon or a theme that compares with `current_page`.
- **`paginate` gives a single page no `parts`.** 1.2.0 gave it one `current` part, so `paginate.parts.size` was 1 and a theme that prints its pagination when there are parts (Dawn's collection list: `if paginate.parts.size > 0`) printed a lone `1`; the parity store prints nothing there (private parity recording `page-collections` of Dawn 16.0.0). `default_pagination` prints nothing for a single page now. To do: nothing.
- **A `form` given a nil or empty `return_to` prints no `return_to` input.** 1.2.0 printed `<input type="hidden" name="return_to" value="" />`, and for `localization` and `currency` that empty input replaced the page's address; the parity store prints no input at all (Horizon 4.3.0's localization form passes `return_to: back` with no `back` variable, private parity recordings of Horizon, every page). A form given no `return_to` is unchanged: `localization` and `currency` still return to the page's address. To do: nothing, unless your theme's script reads the empty input.
- **`content_for` takes `closest.*` parameters.** `{% content_for 'blocks', closest.product: product %}` and the same on `'block'` set what `closest` holds for the blocks it renders, their children and their settings (`closest.collection`, `closest.article`, `closest.blog`, `closest.page`, and `closest.metaobject.<definition type>`); any other `closest.` parameter is an error printed inline (`content_for: closest.thing is not a resource type closest holds`). 1.2.0 passed `closest.product` to a static block as a variable named `closest.product`, which nothing could read, and ignored the parameters of `'blocks'`.
- **A static block rendered again is numbered.** The second time a section or block renders `{% content_for 'block', id: 'card' %}` (in a loop) its `block.id` and wrapper id are `card-1`, the third time `card-2`, and every block rendered inside a numbered one ends with the same number, as the parity store prints Horizon's blog and home pages. 1.2.0 gave every repeat the same id, so a page held duplicate element ids. To do: a theme script that looked a repeated block up by its bare id finds only the first.

**Objects**

- **`page_description` is the shop's description on `/collections` and `/search`.** 1.2.0 gave both pages none, so a theme that prints its description meta only `if page_description` (Horizon 4.3.0, Dawn 16.0.0) printed none there; the parity store prints the shop's description on both (private parity recordings `page-collections` and `page-search` of both themes), as it does on the home page. To do: nothing.
- **A menu prints as its handle.** `{{ linklists['main-menu'] }}` and a `link_list` setting output directly print `main-menu`, as the parity store printed Horizon's `menu="{{ customer_account_menu }}"` (`menu="customer-account-main-menu"`); the direct `linklists[...]` print is the same object and was not recorded on its own. 1.2.0 printed `[object Object]`. `json`, `inspect` and `for` are unchanged. Compare against `.handle` or `.title` instead of the printed text if a template depended on the old text.
- **The form of an existing address starts from the address.** In `{% form 'customer_address', address %}`, `form.first_name`, `last_name`, `phone`, `company`, `address1`, `address2`, `city`, `province`, `country` (the country's name) and `zip` are the address's, HTML-escaped, where 1.2.0 left every one nil unless the visitor had posted it (so editing an address showed empty fields). A posted value still wins, and a new address form (`customer.new_address`, nil) has none.
- **`closest` exists.** The global [`closest`](https://shopify.dev/docs/api/liquid/objects/closest) holds `product`, `collection`, `article`, `blog` and `page` (nil when nothing near has one) and `metaobject.<definition type>`: the resource the nearest `content_for` passed, else the nearest resource setting of the block, its parent blocks or its section (an empty one included, which holds nil), else the template's resource. 1.2.0 had no `closest`, so it read nil everywhere. To do: nothing; a theme that assigned a variable named `closest` keeps its own.
- **A theme block's id has a prefix.** `block.id` and the wrapper id of a block from `blocks/` are `<prefix>__<key>` (`A3kq…__text_1`), as the parity store prints Horizon's, where 1.2.0 printed the bare key, so CSS a theme scopes by `#shopify-block-{{ block.id }}` no longer reaches the block of the same key in another section. The prefix is `A` and 17 letters and digits, a hash of the section id and the keys from the section down to the block: the same on every render, different for each block, and shared by the repeats of a static block (`…__card-1`) and the blocks inside them. The entries of `section.blocks` carry the same id. A block that a section's own schema defines (Dawn's) keeps its key, as on Shopify. The report and error messages still name blocks by key. To do: a theme script or test that looked a block up by its bare key reads `block.id` instead; Shopify's own prefixes are not reproduced (shopify.dev does not document them).
- **`section.shopify_attributes` is the empty string**, as a block's is, and the entries of `section.blocks` have their own `blocks`. 1.2.0 read nil and nothing.
- **`collections.all` is titled `Produits` on a French page**, as the parity store prints it; other languages keep `Products`.
- **A product option's `values` are `product_option_value` objects.** Each value has the `id`, `name`, `available`, `selected`, `variant`, `product_url` and `swatch` that https://shopify.dev/docs/api/liquid/objects/product_option_value documents, where 1.2.0 gave plain strings, so Dawn's and Horizon's variant pickers showed every value sold out and unselected, with an empty `data-option-value-id`. A value still prints, compares (`option.selected_value == value`), joins and escapes as its name. `available` follows the page's tree (whether a variant with the value and the values selected for the options before it can be bought), `variant` is the variant of the value with the other selected values, and the ids are the data's (`ProductData.option_values`) or a hash of the product id, the option and the value, the same on every build. A product page reads `?option_values=<id>,<id>` as Shopify's high-variant pickers send it and selects that variant (an unavailable one too; a combination no variant has selects none), and `options_by_name` finds an option in any case. `product.variants_count` is new. `value.size` is the length of the name, as Horizon's variant picker needs (`--variant-ch: 3.9em` for a six-letter value, where 1.2.0 printed `0.0em`). To do: a template that reads a value as a string through a filter that does not print it (`value.first`) reads `value.name` instead.
- **Menu links have a `handle`.** https://shopify.dev/docs/api/liquid/objects/link documents it; 1.2.0 left it out, so every submenu of Dawn's, Horizon's and our theme's menus got the same id (`HeaderMenu-`) and `aria-controls` pointed at the first. It is `LinkData.handle`, or the link's title handleized in the store's primary language, which a translated menu keeps (Shopify prints `HeaderMenu-news` on its English and French pages). `data_sharing_opt_out_icon` is nil. To do: nothing.
- **The shop has its policies and its password message.** `shop.policies`, `shop.privacy_policy`, `refund_policy`, `shipping_policy`, `subscription_policy` and `terms_of_service` are the `policy` objects of the new `ShopData.policies` (https://shopify.dev/docs/api/liquid/objects/shop and https://shopify.dev/docs/api/liquid/objects/policy), translated by `TranslationsData.policies`, where 1.2.0 had an empty list and nothing else, and `shop.password_message` is `ShopData.password_message`, which 1.2.0 never printed. `/policies/<handle>` renders the policy in the theme's layout (`renderPage` with `templateName: 'policy'`, `request.page_type` `policy`, an empty template name), as Shopify does, and the storefront serves it; `requestFromUrl` routes the address to it where 1.2.0 gave the 404 template. `storefrontSampleData` has the privacy policy the parity store has, and `sampleStoreData` four short policies, so footers that list `shop.policies` and product pages that link `shop.shipping_policy` print them. To do: nothing; a store without policies prints what 1.2.0 printed.
- **Vendor and type collections have `current_vendor` and `current_type`, and Shopify's collections have no id.** On `/collections/vendors?q=` and `/collections/types?q=` the collection's `current_vendor` or `current_type` is the term (https://shopify.dev/docs/api/liquid/objects/collection), so the filter forms of Dawn and our theme keep their `q`; 1.2.0 had neither. `collections.all` and the vendor and type collections print `id` as nil, as the parity store does (`data-collection-id=""`), where 1.2.0 printed `0`. A collection's own image reads the collection's title as its `alt` when it has none, as Shopify prints it (`alt="Men"`). To do: code that tells `collections.all` apart by `collection.id == 0` reads its `handle` instead.
- **Metafields are `metafield` objects.** `resource.metafields.<namespace>.<key>` on a product, variant, collection, page, blog, article, shop and customer has the `value`, `type` and `list?` of https://shopify.dev/docs/api/liquid/objects/metafield, where 1.2.0 gave the stored value, whose `.value` was nil (the review blocks of the three themes read `metafields.reviews.rating.value`). A metafield prints as it is stored, so `{{ product.metafields.custom.material }}` still prints `Cotton`, and the storefront filters read it the same way. A `Metafields` entry is either a plain value, whose type is read from it (a string, a number, a boolean, a list of strings, or JSON), or `{ type, value }` (`MetafieldData`) with a type the page lists, whose `value` is then typed: a `rating` (printing its rating), a `color`, a measurement (printing value and unit), a `rich_text_field` (printing its HTML), `money`, a product, collection, page or variant reference by handle or id (the referenced object, and `count` on a list of them), a `file_reference` image and `json`. To do: a template that compared a metafield with `==` or passed it to a filter as its value still works; one that read `.value` of a value you stored as an object `{ type, value }` of your own now reads the typed value.
- **Variants and cart lines have their unit prices, volume prices and pickup stock.** A variant has `barcode`, `unit_price` and `unit_price_measurement` (from `VariantData.unit_price_measurement`), `quantity_price_breaks` (`VariantData.quantity_price_breaks`, in the view's currency) and `store_availabilities` with their `location` (`VariantData.store_availabilities`), the last on the selected and the first available variant only, nil on the others, as https://shopify.dev/docs/api/liquid/objects/variant says; `product.quantity_price_breaks_configured?` is true when a variant has volume prices. A cart line has `instructions` (`can_remove` and `can_update_quantity` true), no `item_components`, no `parent_relationship`, no `fulfillment`, and the `unit_price` of its final price (https://shopify.dev/docs/api/liquid/objects/line_item); an order line has its variant's unit price. 1.2.0 had none of them. To do: nothing; data without them prints what 1.2.0 printed.
- **Videos have `aspect_ratio` and `duration`, and product images say which variants show them.** A video's `aspect_ratio` is `VideoMediaData.aspect_ratio`, else the width over the height of its first sized source or its preview image, and its `duration` is `VideoMediaData.duration` (milliseconds); an external video has the ratio of its preview image (https://shopify.dev/docs/api/liquid/objects/video, https://shopify.dev/docs/api/liquid/objects/external_video). An image of `product.images` has `attached_to_variant?`, `variants` and `product_id` (https://shopify.dev/docs/api/liquid/objects/image), so Dawn's gallery hides the other variants' media as on Shopify, where 1.2.0 showed all eight of the hoodie's images and Shopify four. To do: nothing.
- **A language has its `direction`.** `request.locale`, `localization.language`, `localization.available_languages` and `shop.published_locales` have the `direction` of https://shopify.dev/docs/api/liquid/objects/shop_locale, `rtl` for a right-to-left language (Arabic, Hebrew, Persian, Urdu and the others written in those scripts) and `ltr` otherwise, so Horizon's `dir="{{ request.locale.direction }}"` is right on a right-to-left store. To do: nothing.
- **A media preview image has no `id`.** `media.preview_image.id` is nil, as the parity store prints it, where 1.2.0 gave the media's id.
- **A product that variant filters narrow has its first matching variant selected.** On a collection or a search under `filter.v.*` filters, a product some of whose variants the filters leave out has `selected_variant` and `selected_or_first_available_variant` set to the first variant that passes them, the variant its `url` and `featured_media` already named, and that variant's `selected` is true; `standard_event_data` then prints it as `"selectedVariant":{…"title":"6"…}` with `"selectedOptions":[{"name":"Size","value":"6"}]`, as the parity store prints Dawn 16.0.0's filtered collection (private parity recording `page-collection-filtered`: high-top-sneakers, one size of which is sold out, and `"selectedVariant":null` for the four products every variant of which passes). 1.2.0 left `selected_variant` nil. A product whose variants all pass, and every product on a page without variant filters, is unchanged. To do: nothing.
- **A line's `properties.size` reads nil.** `item.properties` still iterates as `[name, value]` pairs and answers `item.properties.Engraving`, but its `size` is nil unless a property is named `size`, where 1.2.0 counted the properties (0 for none). Dawn 16.0.0's cart drawer opens its `<dl>` and prints `<p class="product-option"></p>` when `item.properties.size != 0` holds, and the parity store prints `<dl></dl><p class="product-option"></p>` for a line with no properties, no selling plan and only the default variant (private parity recording `ajax-cart-sections` of Dawn, black-sunnies), which only a `size` that is not 0 explains; with 1.2.0 the drawer printed neither. The `size` filter is unchanged (`item.properties | size`). To do: a theme that tests `item.properties.size > 0` should loop over the properties instead.

**Settings**

- **Dynamic sources in setting values resolve.** A section or block setting of a type that takes [dynamic sources](https://shopify.dev/docs/storefronts/themes/architecture/settings/dynamic-sources) (`text`, `inline_richtext`, `richtext`, `url`, `color`, `image_picker`, `video`, the resource settings and their lists) whose saved value or default holds `{{ <object path> }}` reads the object the path names when the setting is read: `"<h1>{{ closest.product.title }}</h1>"` prints `<h1>Hoodie</h1>` on the hoodie's page, `"{{ product.vendor }}"` the vendor, and `"product": "{{ closest.product }}"` is the product. 1.2.0 printed the Liquid as text and read a resource setting that held one as a handle that names nothing. A path may start with `closest`, the template's resource (`product`, `collection`, `page`, `blog`, `article`), `section`, `block`, `shop` and `metaobjects`; a reference to nothing prints nothing, and a resource setting reads nil. A reference to a `liquid` setting reads nil, with `trustLiquidSettings` too, so a dynamic source never runs a theme's code. Text around a reference is made safe as the type's text is, and the value goes in as the resource prints it. A value that holds other Liquid (a filter, a tag, an operator), which Shopify does not accept there ("Additional Liquid is invalid when using this method"), is read as written, as in 1.2.0, and is reported (`invalid_setting`). To do: a theme that printed such values as text on purpose now gets them resolved; nothing else.
- **`color_palette` settings are modelled.** `settings.<id>` of a [`color_palette`](https://shopify.dev/docs/storefronts/themes/architecture/settings/input-settings#color_palette) setting holds its colours by key, each a `color` object, and `for` over it gives the colours in order without their keys: the saved palette, then the default keys it lacks. 1.2.0 gave the saved object as data, so `{{ settings.colors.primary.rgb }}` printed nothing, `{{ settings.colors }}` printed `[object Object]`, and a loop gave `[key, value]` pairs. `{{ settings.colors }}` now prints the colours in order, and `json` each key with its colour. A palette colour that holds `{{ settings.<id>.<key> }}` (what Shopify saves for a deleted colour) is that colour.
- **Palette references in colour settings resolve.** A `color` setting whose saved value or default is `{{ settings.<palette id>.<key> }}` is that palette colour, and a `color_background` value has each such reference replaced by the colour, in global, section and block settings alike. 1.2.0 rejected them as not colours (`invalid_setting`), so Horizon's colour CSS printed `rgb()` with nothing inside. A reference to a key the palette does not have is replaced by the setting's default and reported (`invalid_setting`). To do: nothing.
- **A settings object is not `empty`.** `section.settings != empty`, `block.settings != empty` and `settings != empty` are true for settings that hold a setting, as Horizon's `resource-list` snippet needs; 1.2.0 answered `== empty` true for every settings object, so that snippet printed its error comment and dropped the product cards. A settings object that holds no setting at all is still empty.
- **The resolved settings print through `json`.** `{{ section.settings | json }}` prints a dynamic source's resolved value, not its Liquid.
- **A `url` setting that holds a root-relative path to a page of the store takes the locale prefix.** Under `/fr-ca`, Horizon's `empty_cart_button_link` default `/collections/all` prints `/fr-ca/collections/all`, as the parity store does for that default. Only the root and the paths under `collections`, `products`, `pages`, `blogs`, `cart`, `search`, `policies` and `account` take the prefix; any other path (a file under `/cdn/`, a path that already starts with a market such as `/en-ca/…`) is unchanged, so the prefix is never put on twice. An address with a host, or starting `//`, is unchanged.

**Theme files**

- **Theme JSON files may hold comments and trailing commas.** Templates, section groups, `config/settings_data.json`, `config/settings_schema.json`, the locale files (`locales/*.json` and `locales/*.schema.json`) and the body of a `{% schema %}` tag are read the way shopify.dev says Shopify reads them ([JSON with comments](https://shopify.dev/docs/storefronts/themes/architecture#json-with-comments): "Theme files with JSON support comments and trailing commas"): `//` and `/* */` comments anywhere outside a string, a `//` or `/*` inside a string value (a URL, say) left alone, and a trailing comma before `}` or `]`. 1.2.0 skipped only a `/* */` notice at the top of a file, so a locale file with a `//` comment between its keys, as Shopify's Horizon 4.3.0 ships `locales/en.default.json` and `locales/en.default.schema.json`, did not parse, and every key of the file printed `translation missing: …`. If your theme has such a file, its translations now appear. A file that still does not parse is reported with the file's name and the JSON error, whose position (where it has one) counts from the start of the original text: a locale file or a `{% schema %}` body once per render as an `unsupported` entry (feature `locale_file` or `schema`) while the page renders without it, a section group as an inline Liquid error where its `sections` tag stands, and a template, `settings_data.json` or `settings_schema.json` by rejecting the render.
- **A `t:` default is read for `url`, `video` and `video_url` settings too.** [Schema locale files](https://shopify.dev/docs/storefronts/themes/architecture/locales/schema-locale-files#content) lists `default` as translatable on `html`, `inline_richtext`, `liquid`, `richtext`, `text`, `textarea`, `url`, `video` and `video_url`; 1.2.0 read it for the first six, so a `url` default of `t:settings.link` stayed the string `t:settings.link` and was dropped as an address that is not safe. A `t:` value with no key in the schema locale files is still kept as the string.

**Pages**

- **The storefront links the theme's compiled stylesheet and javascript, as Shopify does.** A page served by the `/storefront` entry links `<base path>/compiled_assets/styles.css?v=<version>` from `content_for_header` (`<link rel="stylesheet" media="screen" …>`) and, when it rendered a section with a `{% javascript %}`, loads `<base path>/compiled_assets/scripts.js?v=<version>` with `<script id="sections-script" data-sections="…" defer="defer" …>`, as the parity store does; the storefront serves both files. 1.2.0 inlined the page's bodies in `<style data-shopify="stylesheet-tags">` and a `DOMContentLoaded` script. `styles.css` holds every section, block and snippet stylesheet of the theme, and `scripts.js` every section's javascript, each run only for the sections the page names. The javascript of blocks and snippets, and a stylesheet in a layout or template, stay inlined. `renderPage` links the files only when it is given `compiledAssetsUrl`, and `CompiledTheme.compiledAssets()` (`compileTheme(theme).compiledAssets()`) gives their bodies and versions (the types `CompiledAssets` and `CompiledFile` are exported); without the option it inlines the bodies as 1.2.0 did. To do: a host in front of the storefront forwards `<base path>/compiled_assets/` to it, as it forwards the pages; a test that read the inlined `<style>` reads the linked file.
- **A page prints `<shopify-store>` before every `<shopify-account>`.** `renderPage` adds `<shopify-store store-domain="<origin>" country="<country>" language="<language>"></shopify-store>` and a line break right before each `<shopify-account` element of the page, as the parity store prints it on every page of Horizon 4.3.0 and Dawn 16.0.0; 1.2.0 printed the theme's account element alone, which Shopify's account component reads its store from. `store-domain` is `request.origin`. A page without an account element is unchanged, and so is `renderSection`. To do: nothing.
- **A policy page carries rules for its layout.** `/policies/<handle>` for a policy the store has set puts two rules in the page's `<style data-shopify="stylesheet-tags">` in `content_for_header`: `.shopify-policy__container` capped at `65ch` and centred, and `.shopify-policy__title` centred. Shopify links a stylesheet of its own for the page; its text is not copied, and these rules are Debutify's own, written for the same layout. Dawn, whose CSS has no `.shopify-policy__*` rule, lays the page out with them; the private theme and Horizon style it themselves. 1.2.0 printed the markup alone. The rules are inlined, not linked: Shopify's address carries a hash that changes with its builds, and a link would fail offline and under a strict `style-src`. To do: nothing.

**Languages**

- **The `date` and `time_tag` formats follow the page's language.** On a page in a language other than English, the named formats are written by `Intl.DateTimeFormat` for it (`format: 'date'` prints `31. Dezember 2018` in German, `2018年12月31日` in Japanese) and `%A %a %B %b` print its day and month names; English prints what it did. A custom `date_formats` key is read from the active language's file and not the default file's, so a language missing a key the default file has prints the engine's error, as the locale files page says Shopify does. A `language_code` posted to `/localization` matches a language in any letter case.
- **`languages: 'theme'` publishes the store in every language its theme has a locale file for.** A new `StorefrontOptions.languages` (`'theme'`; unset keeps the store's own languages) adds, to the languages the store data lists, each language of the theme's storefront locale files (`locales/<language>.json`, `themeLanguages(theme)`; the schema locale files are not storefront languages), with Shopify's name and `endonym_name` (`German` and `Deutsch`, `Portuguese (Brazil)` and `português (Brasil)`, `Chinese (Traditional)` and `繁體中文`), so `localization.available_languages`, the language selectors and `POST /localization` (`language_code`, or Dawn's `locale_code`) offer them, each served at its own subfolder under the base path (`/de`, `/pt-br`, `/zh-tw`). `withLanguages(data, codes)` and `languageOf(iso, primary)` do the same for a caller that renders pages with `renderPage`. The languages go to the primary market only: another market keeps its own, so `/de-ca` is no page. A subfolder is its language tag in lower case (`pt-BR` is `/pt-br`), which `localePrefixes` now writes for every language (no language the store data lists changes, `en` and `fr` being lower case already); an address with `/pt-BR` is no page.
- **A regional locale reads its base language's file, then the default's.** `pt-BR` finds a key in `pt-BR.json`, else `pt.json`, else the default locale's file (1.2.0 read `pt.json` only when there was no `pt-BR.json`), This is Debutify's reading: the [locale files page](https://shopify.dev/docs/storefronts/themes/architecture/locales/storefront-locale-files) says a regional locale "can inherit keys from its base language file" only of Shopify-provided keys, and gives no fallback for a theme's own.

**Storefront**

- **A contextual section group file applies to the page's market.** The storefront now sets `context.market` on every page request of a store whose data has markets, so `sections/header-group.context.<context>.json` with `"market": "<market handle>"` overrides its parent group on the pages of that market (1.2.0 never applied one, because nothing set the context). A store whose theme has such a file with content now renders it for that market.
- **A section asked for at a variant's address is rendered.** `GET /variants/<id>/?section_id=<section>` (and `?sections=`) used to answer the redirect to the product page, so a theme's pickup availability fetch (`/variants/<id>/?section_id=pickup-availability`, in Dawn and in the private theme) read the product page. It now answers the section as any other section request does, with the variant as `product_variant` and no `product`, as [the pickup availability guide](https://shopify.dev/docs/storefronts/themes/delivery-fulfillment/pickup-availability) describes; a variant the store lacks answers 404 with an empty body. The address without a section is unchanged (302).
- **The gift card page has a route.** `GET /gift_cards/<store_id>/<gift_card_token>` (and `HEAD`) is the path [shopify.dev](https://shopify.dev/docs/storefronts/themes/architecture/templates/gift-card-liquid) gives for the page, which Shopify hosts on `checkout.shopify.com`. The storefront serves it under the base path and the locale prefix like any page, and renders the theme's `gift_card` template (which sets its own `{% layout none %}`) with `StoreData.gift_card` as `gift_card`. The card is the one whose `url` has that path, so `gift_card.url` is the address that answers: it now prints the data's `url` under the base path and the locale prefix when that is a path (an absolute one, such as Shopify's own, prints as it is), where 1.2.0 printed the data's value unchanged. A disabled or expired card is shown, which is how the themes mark it (`gift_card.enabled`, `gift_card.expired`). `requestFromUrl` reads the address as the `gift_card` template with the resource `<store_id>/<gift_card_token>`. shopify.dev says nothing of an unknown card or a disabled one. The page is outside the storefront password, as Shopify's checkout domain is: a card the store holds opens on a password-protected store without the password (its sections, and an address that names no card, still go to `/password`). A card's `template_suffix` picks `templates/gift_card.<suffix>.liquid` when the theme has it, as a product's does (a JSON file is never chosen: the [gift card template page](https://shopify.dev/docs/storefronts/themes/architecture/templates/gift-card-liquid) says "This template can't be a JSON template") ([alternate templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/alternate-templates) gives the `<template>.<suffix>` name; the gift card object calls the property "the name of the custom template assigned to the gift card"), and `?view=<suffix>` picks one too. A direct `renderPage` of the `gift_card` template without a request path shows the card at its own `url` (its path, when `url` is absolute) and a card without one at `/gift_cards/1/sample`, so its canonical URL is an address the route serves; 1.2.0 showed `/gift_cards/sample`.
- **The storefront serves Shopify's global assets that the gift card templates load.** `GET <base path>/shopify-assets/<path>` answers `vendor/qrcode.js`, `gift-card/card.svg` and `gift-card/add-to-apple-wallet.svg`, the three files that `shopify_asset_url` is asked for by the private theme, Horizon and Dawn, and 404 for any other path (see [Shopify's global assets](#shopifys-global-assets)). In 1.2.0 `shopify_asset_url` printed `/shopify-assets/<path>` at the host's root and nothing served it, so the card image and the QR code of the gift card page never loaded in a preview. The storefront now gives `shopifyAssetUrl` the default `<base path>/shopify-assets/<path>` unless the caller's `services` set their own, so a page that printed `/shopify-assets/<path>` before prints `/p/<token>/shopify-assets/<path>` under a base path of `/p/<token>`. The files are served whatever the storefront password says, with `Cache-Control: public, max-age=604800` and an `ETag`, where every other answer is `private, no-store`.

## Upgrading from 1.1

1.2.0 is a minor release: everything 1.1.x exports is still exported, and the root entry (`@debutify/liquidjs`) is unchanged. The Shopify layer (`@debutify/liquidjs/shopify`) now prints Shopify's own payment icons and reads Shopify's own font library, where 1.1.x printed Debutify's stand-ins, so a page can come out differently. This is every change a 1.1.x caller can see, with what to do about each. A caller coming from 1.0.x reads this section and [Upgrading from 1.0](#upgrading-from-10) below it, which describes 1.1.0.

**Filters**

- **`payment_type_svg_tag` prints Shopify's icons.** With the default `paymentTypeSvg` service the icon is the file Shopify prints for the type: the files of [activemerchant/payment_icons](https://github.com/activemerchant/payment_icons) at commit `fc8c830` (904 types, and `bogus`, the one file outside its list), byte for byte as the parity store printed them (fixtures `page-home`, `ajax-cart-sections` and `probe-payment-icons`), each with its own artwork, its own `<title>` and its own ending (a line break after `</svg>`, an `<?xml version="1.0"?>` line before `<svg`, where the file has one). 1.1 drew one neutral outline box for every type, titled with the card's name for six cards (`Visa`, `Mastercard`, `American Express`, `PayPal`, `Diners Club`, `Discover`) and with the type's key for any other. A type outside the set prints what Shopify prints for it, the `generic` icon: a grey card with `<title id="pi-generic">Generic</title>` and nothing in it that names the type asked for; the empty string and a capitalised `Visa` print the same (fixture `probe-payment-icons`: its `unknown`, `empty` and `upper` entries are all the string of its `generic` entry). This is the first filter `shopifyFilterRegistry()` lists as `exact`. To do: nothing; a `paymentTypeSvg` of your own is printed as it returns.
- **The default `fontInfo` is Shopify's font library.** The 2,109 handles that shopify.dev lists (261 families) are known, each with the family, fallback families, weight, style, baseline ratio, system flag, variants and files that the parity store prints for it (fixtures `probe-fonts-library` and `probe-fonts-retired-1` to `-4`). 1.1 read any `<family>_<style><weight>` as a font and guessed the rest: the fallback families `sans-serif`, a baseline ratio of 0, and as variants the handle itself plus regular, italic, bold and bold italic, whether the family has them or not. What a caller can see:
  - A handle outside the library is unknown, as an unreadable one was in 1.1: `font_url`, `font_face` and `font_modify` give nothing and report it, and a `font_picker` setting that holds it is nil. `assistant_i4` (Assistant has no italics) and `foo_n4` were fonts in 1.1 and are not now.
  - Variants are the family's real ones: `font_modify: 'style', 'italic'` on Assistant is nil, where 1.1 gave `assistant_i4`.
  - A retired handle renders and prints as the font Shopify renders in its place: `harmonia_sans_n4` is Poppins, and a `font_picker` setting that holds it prints `poppins_n4`. That printed handle is Debutify's choice and not a recording (the font probes print no handle back). Three retired handles, `memphis_i3`, `memphis_i5` and `memphis_i7`, are unknown, because Shopify cannot find them either.
  - A system font (`mono`, `serif`, `arial_n4`, `system_ui_n4` and the rest) prints the empty string for `font_url` in both formats, as the parity store does; the filter decides that before it asks the service, so a host's own `fontUrl` is not called for a system font. `font_face` of one prints nothing. In 1.1 `arial_n4` was an ordinary font with a file under `/fonts/`, and `mono` and `serif` were unknown.
  - To do: a caller whose themes name fonts outside Shopify's library passes its own `fontInfo`, which can call `shopifyFontInfo` first and answer the other handles itself.
- **`font_url` and the default `font_face` point at the library's files.** The address is `/fonts/<directory>/<file>` (`/fonts/assistant/assistant_n4.9120912a469cad1cc292572851508ca49d12e768.woff2`) where 1.1 wrote `/fonts/<handle>.<format>` (`/fonts/assistant_n4.woff2`). `FontInfo.files` holds the two paths (`woff2` and `woff`), relative to `https://fonts.shopifycdn.com/`, which serves them; a font without `files`, such as one your own `fontInfo` returns, keeps `/fonts/<handle>.<format>`. To do: serve `https://fonts.shopifycdn.com/<files>` at `/fonts/`, or set `services.fontUrl` to where the files are; a host that proxies them checks each path with `isShopifyFontFile` first and fetches nothing else.

**Types**

- **The fonts the default `fontInfo` returns are frozen and shared.** There is one object per handle, and one `variants` array for every font of a family, so changing one fails: `info.variants.push('x')` and `info.variants.sort()` throw, and an assignment to a field throws in strict mode code and is ignored otherwise. `FontInfo.variants` is now `readonly string[]`, so code that edits it, or passes it where a `string[]` is expected, stops type-checking; `FontInfo.files` is new and typed `Readonly<…>`. To do: copy before changing (`[...info.variants].sort()`).

**Storefront**

- **The storefront's `services` may be a function of the request.** `createStorefront({ services })` takes a `Partial<ShopifyServices>` as before, or a function of the request that returns one, called once per request like `theme` and `data`; a host that serves many base paths from one storefront uses it to put the base path into `assetUrl` and `fontUrl`. To do: nothing.

**New, with nothing to change**

- `shopifyPaymentIcon`, `shopifyFontInfo` and `isShopifyFontFile` are exported from `@debutify/liquidjs/shopify`: the default `paymentTypeSvg` and `fontInfo` services, and the path check. `FontInfo` has the optional `files`.
- The package has an internal entry, `@debutify/liquidjs/shopify-library` (`dist/shopify-library.js`, about 4.8 MB: the icons and the font library as data), that both `/shopify` bundles load by the package's name, so the data ships once. It is not part of the public API; a host that copies only some of the package's files must keep it, and `NOTICE.md` carries the licence of the icons. It is CommonJS, also under the `/shopify` ESM build, so a bundler that reads the `module` condition needs CommonJS interop (Rollup with `@rollup/plugin-commonjs`, which webpack, esbuild and Vite do on their own); loading it adds about 30 ms and 16 MB the first time `/shopify` is imported.

## Upgrading from 1.0

1.1.0 is a minor release: everything 1.0.x exports is still exported, and the root entry (`@debutify/liquidjs`) renders as it did in 1.0.1 with the default options (the one change under `numberSemantics: 'ruby'` is listed first). The Shopify layer (`@debutify/liquidjs/shopify`) now prints what Debutify's parity store prints where 1.0.x printed something else, so a page can come out differently. This is every change a 1.0.x caller can see in 1.1.0, with what to do about each; the sample store comes first because it is the one most callers meet. Going on to 1.2.0, which changes the payment icons again and adds the font library, read [Upgrading from 1.1](#upgrading-from-11) as well.

**Root entry**

- **`json` and `jsonify` print a decimal with its point under `numberSemantics: 'ruby'`.** `{{ 2.0 | json }}` and `{{ 10 | divided_by: 5.0 | json }}` print `2.0`, as Ruby writes a Float, where 1.0.1 printed `2`, in an array or an object as well; a whole number, a string and the default `numberSemantics: 'js'` print as before. A runtime without `JSON.rawJSON` (Node before 21; this package needs Node 24) keeps the plain number. To do: nothing, unless a template compares the `json` text byte for byte; a JSON parser reads both as one number.

**Sample data**

- **The sample store is mock.shop's.** `sampleStoreData`, and the `data` that `renderPage` and `renderSection` fall back on, is now Shopify's mock.shop `demostore` catalogue (29 products such as `black-sunnies`, the collections `men`, `women`, `unisex`, `tops`, `bottoms`, `accessories`, `featured` and `shoes`, the pages `contact` and `liquid`), where 1.0.x had three products (`classic-tee`, `canvas-bag`, `ceramic-mug`), the collections `frontpage` and `apparel` and the pages `about` and `contact`. The 1.0.1 README's example, `request: { resource: 'canvas-bag' }`, finds no product any more. The collections' descriptions hold a plain apostrophe (`Liquid's`), as the parity store prints them, not the `&#39;` the Storefront API writes. To do: pass your own `data`; to keep rendering the old sample, take it from the 1.0.1 package once (`JSON.stringify(sampleStoreData)` is plain JSON) and keep it in your repository.

**Filters**

- **Image addresses have no protocol.** `image_url`, `img_url` and the `srcset` of `image_tag` (with the default `imageUrl` service), an image's `src`, `{{ image }}` and the image addresses in `product | json` print `//cdn.shopify.com/…`, as the parity store does, where 1.0.x printed `https://cdn.shopify.com/…`. A browser reads both the same. To do: where the address leaves a browser (an email, a feed, the content of an `og:image` tag), put `https:` in front of it, as a theme does with `image_url | prepend: "https:"`. A custom `imageUrl` service still receives the data's own address, with its `https:`, and returns what it likes.
- **`image_url` keeps the size the template asked for.** a request for `width: 1500` of an image 1024 wide prints `width=1500`, as the parity store does, where 1.0.x cut it to `width=1024`; the CDN serves nothing larger than the original. Only the 5760 maximum limits `width` and `height` now. A custom `imageUrl` service therefore receives a `params.width` or `params.height` that can be larger than the image, and decides what to do with it. (`image_tag` follows the URL's size from 1.3.0 on.) To do: a service that builds resizing URLs cuts the size to `image.width` itself if it needs to.
- **`payment_type_svg_tag` names the card.** With the default `paymentTypeSvg` service the icon's `<title>` is the card's name (`Visa`, `Mastercard`, `American Express`, `PayPal`, `Diners Club`, `Discover`; another type keeps its key) where 1.0.x wrote the key, and the icons of Visa, Mastercard and American Express end with a line break after `</svg>`, as Shopify's do. 1.2.0 prints Shopify's own icons instead, see [Upgrading from 1.1](#upgrading-from-11). To do: nothing; a service of your own is printed as it returns.
- **`link_to` writes `rel="nofollow"` only for an external address.** For a root-relative or relative address (`<a href="/">`) 1.0.x wrote `rel="nofollow"` and 1.1.0 writes none, as the parity store prints it. To do: nothing, unless a test compares that markup.
- **Dates print the day without a leading zero.** `date` with a named format (`date`, `abbreviated_date`, `on_date`, `date_at_time`, `default`) and `time_tag` with no format print `February 7, 2023` and `Feb 7, 2023` where 1.0.x printed `February 07, 2023` and `Feb 07, 2023`; only `format: 'date'` is recorded on the parity store, and the other formats take the same unpadded day by assumption. To do: a template that wants the padded day writes the directives itself (`date: '%B %d, %Y'`), which prints as before.
- **`default` follows Ruby's.** An empty hash (`shop.metafields`) takes the fallback, where 1.0.x printed `[object Object]`, and an HTML-safe value such as the output of `image_tag` stays HTML-safe through it, so a later `escape` leaves it as it is where 1.0.x escaped it. To do: nothing.
- **`json` of nil prints `null`.** `{{ missing | json }}` and `{{ nil | json }}` print `null`, where 1.0.x printed nothing and `{}`. To do: a template that relied on the empty output tests the value first.
- **`product | json`, `cart | json`, line items, variants and images through `json` print the parity store's shapes**, their keys in its order and with its fields (for example a product's `options` as the option names, no `url`, and `content` last), where 1.0.x printed the engine's own drop shapes. To do: code that reads the JSON by key keeps working unless it read a field Shopify's shape lacks; compare any stored snapshot.
- **`font_face` ends its rule with a line break**, where 1.0.x ended it with `}`. To do: nothing, unless a test compares the rule.

**Objects and pages**

- **Lists come in Shopify's order.** `{% for c in collections %}` lists the collections by title, `collections['all'].products` comes by title and a collection that has a `sort_order` lists its `products` in that order wherever they are read (not only on its own page), and `blog.articles` lists the newest article first, where 1.0.x kept the data's order in each. To do: nothing, unless a template relied on the data's order; a collection keeps its products in the data's order with `sort_order: 'manual'`, and a template that needs another order sorts the list itself.
- **Page metadata is the text.** `page_description` is the text of the description (tags out, white space collapsed, the first 320 characters), where 1.0.x printed the raw HTML, and `page_title` and `canonical_url` are Shopify's for the cart, collections, 404 and search pages (`Your Shopping Cart`, `Collections`, `404 Not Found`, `Search: 5 results found for "shirt"`). To do: nothing.
- **A request's `view` or a resource's `template_suffix` renders the alternate template** when the theme has it (`templates/product.probe.json` for a suffix `probe`), where 1.0.x rendered the base template. The ids of its sections follow (`template--product-probe__main` for `template--product__main`), and `RenderPageResult` and `RenderSectionResult` have a `templateName` that names the template that rendered. To do: nothing, unless you looked sections up by id for such a resource.
- **`paginate` past the last page shows no items**, with `current_page` the page asked for, where 1.0.x showed the last page; its `next` and `previous` links keep the request's query, ordered by name, where 1.0.x wrote only `?page=n`. To do: nothing.
- **Cart line keys are `<variant id>:<32 hex digits>`** (`43696926949398:64656d37dd2ad316b3e09febf0b4dff2`), where 1.0.x wrote `3001:1`, and a line with a quantity under 1 is dropped. The hash is Debutify's, not Shopify's. To do: treat a key as opaque, and do not keep keys written by 1.0.x.
- **`content_for_header` has more in it.** It now prints `Shopify.analytics` on every page, and for data with several markets the `hreflang` links, the market's currency and a `Shopify.routes.root` with the locale prefix. To do: nothing, unless a test compares the head byte for byte.

**Tags and settings**

- **`form 'contact'` and `form 'customer'` anchor at the form's `id`.** With `id: 'ContactForm'` the action is `/contact#ContactForm`, where 1.0.x always wrote `/contact#contact_form`; without an `id` it is still `/contact#contact_form`. To do: nothing.
- **`form 'localization'` and `form 'currency'` return to the whole address.** Their `return_to` is the page's path and query, where 1.0.x wrote the path alone, and it is written with the `&` between the parameters raw (`/collections/all?a=1&b=2`), as the parity store does; a `"`, `<` or `>` in a path is percent-encoded, so nothing in it can end the attribute. An explicit `return_to:` argument is still escaped. To do: nothing.
- **`form 'product'` with a quoted key prints nothing, its body included.** `{% form 'product', all_products['black-sunnies'] %}x{% endform %}` printed a working form in 1.0.x and prints `""` now, as the parity store prints an empty body (whether it drops a non-empty body too is still to confirm). To do: assign the product first, `{% assign product = all_products['black-sunnies'] %}{% form 'product', product %}`.
- **A sanitised setting keeps the closing of a void tag as it was stored.** `richtext`, `inline_richtext` (always), an `html` setting and a text setting with markup (in untrusted mode) keep `<br/>`, `<hr/>` and `<img src="x"/>` as written (and ` />` with a space), where 1.0.x wrote `<br>`, `<hr>` and `<img src="x">`; a tag stored without the slash stays without it, as the parity store prints the `<br/>` a theme stores. To do: nothing.
- **A saved `select` or `radio` setting keeps a value that is no longer one of its options** (a plain token, in untrusted mode), where 1.0.x replaced it with the default and reported it, as the parity store keeps it. To do: nothing.

**Types**

- **`CartData` is a union.** `StoreData.cart` is now `CartLinesData | CartState`: the lines by product handle and variant id that 1.0.x had (now exported as `CartLinesData`) or a visitor's `CartState`. Data written for 1.0 still type-checks; code that reads `data.cart.items[0].product_handle` narrows first (`'items' in cart`), and `interface X extends CartData` becomes `extends CartLinesData`.
- **`CompiledTheme` members other than `templates(path)` are internal**, as the README's Public API section says; `files` is now `own`.

**New, with nothing to change**

- **The `@debutify/liquidjs/storefront` entry is new**, and so are the discount data (`StoreData.discounts`), the shipping zones and the markets: no 1.0.x data uses them. A discount applies to one-time purchases only unless its `applies_on_subscription` is `true` (and `applies_on_one_time_purchase: false` takes one-time purchases out).

## Shopify themes: `@debutify/liquidjs/shopify`

The `/shopify` entry point renders Shopify Online Store 2.0 themes without a Shopify store: a preset engine with Shopify's tags and filters, store objects built from data you pass in, and a theme runtime that renders whole pages or single sections and reports what it could not render faithfully. The root entry, `@debutify/liquidjs`, stays plain LiquidJS.

With the Shopify layer, import `Drop`, `LiquidFloat` and any other engine class from `@debutify/liquidjs/shopify`; a Drop built on the root entry's class reads as empty under the preset.

The `./shopify` entry of the package's `exports` map has `types`, `module` and `default` conditions, and no `import` or `require` condition. Bundlers that read `module` take the ES module build, `dist/shopify.node.mjs`; plain Node, whether the caller uses `import` or `require`, takes `default`, the CommonJS build `dist/shopify.node.js`. The `/shopify` entry is for Node: it imports Node's `stream`, `path`, `fs`, `module` and `crypto` and has no browser build, which the root entry keeps.

What each tag, filter and object prints follows its page in shopify.dev's [Liquid reference](https://shopify.dev/docs/api/liquid); where shopify.dev does not pin an output, the package follows the closest documented behaviour or Shopify Liquid's own tests, and the case is listed under [Behaviours still to confirm on Shopify](#behaviours-still-to-confirm-on-shopify).

The preset parses templates as Shopify's storefront does. Its whitespace control is bug-compatible (`bugCompatibleWhitespaceTrimming`): a heading that prints `{{ heading }}`, a newline and `{%- if accent -%}` keeps that newline, as liquid-spec's Dawn recordings and Shopify's own Dawn demo store show. An `if`, `unless`, `case` or `for` whose every branch is blank, holding only whitespace and tags that print nothing (`assign`, `capture`, `comment`, an empty `raw` or `doc`, and blocks as blank as these), prints nothing at all, as Ruby Liquid drops the text of such a block (`remove_blank_strings` in Shopify/liquid's `if.rb`, `for.rb` and `case.rb`); a `tablerow` keeps its text, as in Ruby.

### Render a page

Run this as an ES module (a `.mjs` file, or `"type": "module"` in `package.json`).

```js
import { renderPage, renderSection } from '@debutify/liquidjs/shopify'

const theme = {
  files: {
    'layout/theme.liquid': '<!doctype html><html><head>{{ content_for_header }}</head><body>{{ content_for_layout }}</body></html>',
    'templates/product.json': '{ "sections": { "main": { "type": "main-product" } }, "order": ["main"] }',
    'sections/main-product.liquid': '<h1>{{ product.title }}</h1>{{ product.price | money }}<link rel="stylesheet" href="{{ "product.css" | asset_url }}">{% schema %}{ "name": "Product" }{% endschema %}'
  }
}

const services = { assetUrl: (path) => `https://cdn.example.com/assets/${path}` }

const { html, report } = await renderPage({ theme, templateName: 'product', request: { resource: 'black-sunnies' }, services })
// html ends with <body><div id="shopify-section-template--product__main" class="shopify-section"><h1>Black Sunnies</h1>$50.00<link rel="stylesheet" href="https://cdn.example.com/assets/product.css"></div></body></html>
// report.errors is [] and report.sections[0].status is 'rendered'

const { html: section } = await renderSection({ theme, templateName: 'product', section: 'main', request: { resource: 'black-sunnies' }, services })
// section is <div id="shopify-section-template--product__main" class="shopify-section"><h1>Black Sunnies</h1>$50.00<link rel="stylesheet" href="https://cdn.example.com/assets/product.css"></div>
```

From CommonJS, which has no top-level `await`, use `require` with `.then` (with the `theme` and `services` objects from above):

```js
const { renderPage } = require('@debutify/liquidjs/shopify')

renderPage({ theme, templateName: 'product', request: { resource: 'black-sunnies' }, services }).then(({ html }) => console.log(html))
```

`theme.files` holds every file of the theme by path; the package never reads the file system. Keep the same `theme` object between renders: it is parsed once, and a file you edit in `theme.files` is re-parsed on the next render. Without `data`, pages render with the package's public sample store (`sampleStoreData`): Shopify's mock.shop `demostore` catalogue (https://mock.shop), 29 apparel products such as `black-sunnies` (Black Sunnies, $50.00), the collections `men`, `women`, `unisex`, `tops`, `bottoms`, `accessories`, `featured` and `shoes`, the pages `contact` and `liquid`, the blog `news` and the `main-menu`, `footer` and `customer-account-main-menu` menus, which is why `request: { resource: 'black-sunnies' }` finds a product in the example. Its product images are on Shopify's CDN. To render your own store, pass `data`, a `StoreData` object (an exported type, with `sampleStoreData` as a model of one; `sampleStoreData` is frozen all the way down, so to change it pass a copy, `data: structuredClone(sampleStoreData)`, edited first). `t` reads translations from `locales/<locale>.json`, `locales/<locale>.default.json` and the `.schema.json` variants in `theme.files`. A template the theme does not have rejects.

The options of `renderPage` are `theme`, `templateName` (`index`, `product`, `page.contact`, `customers/login`; a base name renders the alternate template the request picks, see [Storefront requests](#storefront-requests)), `data` (a `StoreData` object), `locale` (the theme's locale file; the content follows `request.language`), `request` (a `RequestInput`, which `requestFromUrl` reads from a storefront address: the resource, the market and language, the query and the rest, see [Storefront requests](#storefront-requests)), `cart` (a visitor's `CartState`, in place of `data.cart`), `services`, `trustLiquidSettings`, `trustHtmlSettings`, `unknownTags`, `parseLimit`, `renderLimit`, `memoryLimit`, `viewCacheSize` (the views of `data` kept for later renders, default 16, see [Storefront requests](#storefront-requests)) and `compiledAssetsUrl` (the address the theme's compiled `{% stylesheet %}` and `{% javascript %}` files are served under, ending in `/`: with it `content_for_header` links them as Shopify does, and without it inlines the page's bodies; serve `compileTheme(theme).compiledAssets()` there, as the [`/storefront` entry](#storefront-debutifyliquidjsstorefront) does). It returns `html`, `report` and `templateName`, the template that rendered. `renderSection` takes the same options plus `section`: the id `renderPage` reports for it (`template--product__main`), a key of the template's `sections` (`main`) or the name of a static section. It returns `html`, `report`, `templateName` and `assets`, the bodies of the `{% stylesheet %}` and `{% javascript %}` tags that ran while the section rendered. A section the page does not have renders nothing and is reported.

The templates follow shopify.dev's [JSON templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/json-templates), [section groups](https://shopify.dev/docs/storefronts/themes/architecture/section-groups), [section schema](https://shopify.dev/docs/storefronts/themes/architecture/sections/section-schema) and [theme blocks](https://shopify.dev/docs/storefronts/themes/architecture/blocks/theme-blocks) pages, and `renderSection` the [Section Rendering API](https://shopify.dev/docs/api/ajax/section-rendering), which returns a section's HTML alone. The bodies of `{% stylesheet %}` and `{% javascript %}` tags are inlined into `content_for_header`; shopify.dev says Shopify serves them [through `content_for_header`](https://shopify.dev/docs/storefronts/themes/best-practices/javascript-and-stylesheet-tags), and inlining them is Debutify's choice.

Theme JSON files may hold `//` and `/* */` comments and trailing commas, as shopify.dev says [Shopify's theme files can](https://shopify.dev/docs/storefronts/themes/architecture#json-with-comments): templates, section groups, `settings_data.json`, `settings_schema.json`, locale files and the body of a `{% schema %}` tag. A file that does not parse after that is reported, with its name and the JSON error (its position, where it has one, counts from the start of the original text): a locale file (`unsupported`, feature `locale_file`) and a schema (feature `schema`) once per render, and the render goes on without them, so a locale file that does not parse leaves every key of its language missing; a section group (an inline Liquid error where its tag stands); a template, `settings_data.json` or `settings_schema.json` rejects the render.

### Render one template or snippet

```js
import { createShopifyLiquid, renderLiquid } from '@debutify/liquidjs/shopify'

const liquid = createShopifyLiquid({ files: { 'snippets/price.liquid': '{{ price | money }}' } })
const { html, report } = await renderLiquid(liquid, "{{ 1999 | money }} {{ 10 | divided_by: 4 }} {{ 'Hello World' | handleize }} {% render 'price', price: 500 %}")
// html is "$19.99 2 hello-world $5.00" and report.errors is []
```

`files` holds the snippets and layouts that `render`, `include` and `layout` read (`{% render 'price', price: 500 %}` reads `snippets/price.liquid`). `renderLiquid(liquid, source, scope)` starts every call from a fresh state, so two renders never share a report, and its `scope` is the template's scope; it takes no render options. With `liquid.parseAndRender(source, scope, { globals })`, the globals you pass replace the engine's `globals` option, as in LiquidJS; the preset keeps its own Shopify state either way. `createShopifyLiquid` takes `files`, `services`, `translator`, `moneyFormat`, `moneyWithCurrencyFormat`, `unknownTags`, `parseLimit`, `renderLimit`, `memoryLimit` and `engine`, a LiquidJS options object applied last, over the preset. Trusted mode for settings is not among them: settings objects are built by `renderPage` and `renderSection`, which take it (see [Safety](#safety)).

### Storefront requests

A storefront answers addresses: pages, and the [Ajax API](https://shopify.dev/docs/api/ajax)'s JSON. The engine reads an address into the request a page renders, builds the store's objects once per market, language and URL prefix, and prints the Ajax answers from the same objects a page shows, so a page and its `/cart.js` agree. Serving the addresses, keeping a visitor's cart and handling posts are the caller's; the [`/storefront` entry](#storefront-debutifyliquidjsstorefront) does all three.

`requestFromUrl(url, data, options?)` reads an address as Shopify routes it and returns a `PageRequest`: the base template to render (`templateName`), the `request` for `renderPage` and the `locale` the page renders in. `options` takes `basePath` (a path the store is served under, such as `/p/<token>`, taken off before routing), `country` (the shopper's chosen country, kept when it belongs to the address's market) and `form` (the outcome of a form posted before this page).

```js
import { renderPage, requestFromUrl, storefrontSampleData as data } from '@debutify/liquidjs/shopify'

const page = requestFromUrl('/fr-ca/collections/tops?sort_by=price-ascending&page=2', data)
// page.templateName is 'collection' and page.locale 'fr'
// page.request is { path: '/fr-ca/collections/tops', query: [['sort_by', 'price-ascending'], ['page', '2']], basePath: '', localePrefix: '/fr-ca', market: 'ca', language: 'fr', country: 'CA', page: 2, sortBy: 'price-ascending', filters: [], resource: 'tops' }
const { html, templateName } = await renderPage({ theme, templateName: page.templateName, data, request: page.request, locale: page.locale })
```

It routes `/` (`index`), `/products/<handle>`, `/collections` (`list-collections`), `/collections/<handle>` and its tag paths (`/collections/<handle>/<tag>+<tag>`), `/collections/<handle>/products/<product>` (the product page, with that collection as the `collection` global), `/collections/vendors?q=` and `/collections/types?q=`, `/pages/<handle>`, `/gift_cards/<store_id>/<gift_card_token>` (the `gift_card` template, with the resource `<store_id>/<gift_card_token>`), `/blogs/<blog>`, `/blogs/<blog>/tagged/<tag>`, `/blogs/<blog>/<article>`, `/search` (with `q`, `type`, `options[prefix]` and `options[unavailable_products]`), `/search/suggest` (the `search` template with a `predictive` request), `/recommendations/products` (the `index` template with a `recommendations` request, for the section it names), `/cart` and `/password`; any other address is the `404` template. `/variants/<id>` is one of those: Shopify answers it with a redirect to `/products/<handle>?variant=<id>` (fixture `flow-variant-route`), which is the caller's to send. The locale prefix (`/fr-ca`) is taken off first; `localePrefixes(data)` lists every prefix the store serves, the primary market's other languages at `/<language>` and each other market at `/<language>-<subfolder>`, each a `LocalePrefix` (`prefix`, `market`, `language`). `?page=`, `?view=`, `?sort_by=`, `?variant=`, `?selling_plan=` and the `filter.*` pairs are read on every page, and `contact_posted=true` or `customer_posted=true` shows the contact or newsletter form as posted.

Every field of `RequestInput` is optional, so a request built by hand needs only what it uses. `path`, `host`, `origin` and `query` (the address's pairs, in order) say where the page is; `basePath`, `localePrefix`, `market`, `language` and `country` which view and which shopper; `resource` (the handle of the product, collection, page or blog, `<blog>/<article>` for an article, or an order's name, number or id on `customers/order`; the first one in the store when omitted), `collection`, `tags`, `page`, `variant`, `sellingPlan`, `view`, `sortBy`, `filters` (the `filter.*` pairs), `searchTerms`, `search` (`types`, `prefix`, `unavailable`) and `productVariant` (the variant a Section Rendering request on `/variants/<id>` reads as `product_variant`) what it shows; `predictive` (a `PredictiveRequest`) and `recommendations` (a `RecommendationsRequest`: `productId`, `limit`, `intent`) the two requests a section answers; `form` (a `FormOutcome`: the form's `type`, whether it was `posted`, its `errors` by field and the posted `values`) what a form posted before the page gave; and `context` which contextual section group files apply (`header-group.context.<market>.json`).

**Views.** A store renders in a view, a `StoreView` (`market`, `language`, `prefix`), which `resolveView(data, request)` takes from a request: the market and language it names, otherwise the primary market and that market's first language, and the prefix `basePath` then `localePrefix`. The market sets the currency and the prices (converted at its rate and rounded as the parity store rounds them, CAD to whole units and EUR up to `.95`), the language the content translations (`StoreData.translations`) and the names of countries and languages, and the prefix every URL the store prints. The objects of a view are built the first time a request needs them and kept for that `data` object, the 16 views used most recently by default, so pass the same `data` object to every request and a new object when the data changes: data edited in place keeps rendering the objects built before the edit.

```js
import { productJson, resolveView, storefrontSampleData as data } from '@debutify/liquidjs/shopify'

const view = resolveView(data, { market: 'ca', language: 'en', localePrefix: '/en-ca' }) // { market: 'ca', language: 'en', prefix: '/en-ca' }
productJson(data, 'hoodie', view).price // 12200: 90.00 USD at 1.35 is 121.50, rounded up to 122.00 CAD
productJson(data, 'nope') // null: /products/nope.js answers 404
```

**The view cache.** Every URL in a view's objects sits under its prefix, so a store served under many base paths (a preview for each `/p/<token>`, say) builds a view for each path, and each view is a full copy of the store. Measured on a generated store of 5,000 products with 45,000 variants, 100 collections and the dataset's seven filters, a view holds 40 MB (about 8 KB per product with its nine variants) and takes about 120 ms to build, so the 64 views the engine kept before this limit came to 2.6 GB for one `data` object, and the default 16 come to about 640 MB. A view that has been searched also keeps the words of its products, 7 MB for `renderPage`'s search and 9 MB for `predictiveJson` on that store (its descriptions repeat a 16-word vocabulary, so a real catalogue holds more). `viewCacheSize` sets how many views a `data` object keeps, on `renderPage` and `renderSection` or by calling `setViewCacheSize(data, size)`; the storefront takes it as its own `viewCacheSize` option. It is a whole number of at least 1 (`Infinity` for no limit), set on the `data` object: the latest call that names a size decides, a call that names none leaves it, and views beyond a smaller size are dropped at once, the least recently used first. A request whose view was dropped builds it again before its first page, so a size below the number of base paths in use costs the build on every request. The base path is not taken out of the built objects: it is in the URL of every product, variant, collection, page, blog, article, menu link, cart line, route, filter and pagination link, each a plain string that themes compare, cut and pass to filters, so applying it where a URL is printed would mean rebuilding all of those builders and what a template may do with a URL.

**Ajax answers.** Each takes the store `data` and a `view` that defaults to the primary market's, and returns plain JSON. `productJson(data, handle, view?)` is `/products/<handle>.js`, null for a handle the store does not have. `oembedJson(data, 'product' | 'collection', handle, view?)` is `/products/<handle>.oembed` or `/collections/<handle>.oembed` as text, null for a handle the store lacks. `predictiveJson(data, request.predictive, view?)` is `/search/suggest.json`. `recommendationsJson(data, request.recommendations, view?)` is `/recommendations/products.json`. `cartJson(data, cart, view?, form?)` is `/cart.js`, and with `form` `'change'` the cart in the answers of `/cart/add.js`, `/cart/change.js` and `/cart/update.js`, whose `items_added`, `items_removed`, `items_changelog` and `sections` the caller adds. `discountCodeStatus(data, cart, view?)` is those answers' `discount_codes`: each entered code, as entered, and whether it applies. `shippingRates(data, cart, address, view?)` is `/cart/shipping_rates.json` and `/cart/async_shipping_rates.json` for an `address` of `country` (an ISO code or an English name), `province` and `zip`: `{ shipping_rates: [...] }`, or the error Shopify answers with status 422 for an address no zone covers, `{ country: ['Country/region not supported'], zip: ['Enter a postal code'] }` (`zip` only when none was given). `lineItemJson(item, form?)` prints one line of a cart object (an item of `cart.items`) in the form of `/cart.js` (`'cart'`, the default), of the add and change answers (`'change'`) or of `{{ cart | json }}` (`'liquid'`); `cartJson` prints its lines with it.

```js
import { predictiveJson, requestFromUrl, storefrontSampleData as data } from '@debutify/liquidjs/shopify'

const suggest = requestFromUrl('/search/suggest?q=shirt&resources[type]=product', data)
predictiveJson(data, suggest.request.predictive).resources.results.products.map(p => p.handle) // ['men-t-shirt', 'women-t-shirt', 'workout-shirt']
```

**The visitor's cart.** A cart is plain JSON the caller keeps between requests, a `CartState`: a `token`, its `lines` (each a `CartLineState`: `variantId`, `quantity`, `properties` and `sellingPlanId`; a new line goes first, as Shopify lists it), a `note` (`null` until the cart first changes), `attributes` and the entered `discountCodes`. `RenderPageOptions.cart` shows it on a page in place of `StoreData.cart`, priced in the view's currency with `StoreData.discounts` and the entered codes applied, and `cartJson` prints the same cart. The caller changes a cart by editing its state: `findVariant(data, id)` gives a variant and its product (null for an id the store does not have), `stockFor(variant)` how many of it can be sold (`0` when it is not available, `null` when its stock is not tracked or it sells past zero), and `lineKey(line)` a line's key, `<variant id>:<32 hex digits>`, the same for the same properties and selling plan, which the Cart API's `id` parameter can name.

```js
import { cartJson, discountCodeStatus, findVariant, renderPage, stockFor, storefrontSampleData as data } from '@debutify/liquidjs/shopify'

const cart = { token: 'c1', lines: [{ variantId: 43695847538710, quantity: 2, properties: {}, sellingPlanId: null }], note: null, attributes: {}, discountCodes: ['WELCOME10'] }
findVariant(data, 43695847538710).product.handle // 'hoodie'
stockFor(findVariant(data, 43695847538710).variant) // 42
cartJson(data, cart).total_price // 16200: two hoodies at 90.00, less 10%
discountCodeStatus(data, cart) // [{ code: 'WELCOME10', applicable: true }]
const { html } = await renderPage({ theme, templateName: 'cart', data, cart })
```

**Templates.** For a base `templateName` (`product`), `renderPage` renders the alternate template the request's `view` names (`?view=probe` renders `templates/product.probe.json` or `.liquid`), else the one the resource's `template_suffix` names, when the theme has it, else the base template ([alternate templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/alternate-templates)). `RenderPageResult.templateName` and `RenderSectionResult.templateName` say which rendered, and `template.name` and `template.suffix` print it, as the parity store does (fixtures `probe-product-suffix` and `probe-collection-suffix`). A view or suffix holding `/` names no template.

```js
const { templateName } = await renderPage({ theme, templateName: 'product', data, request: requestFromUrl('/products/white-leather-sneakers', data).request })
// 'product.probe' when the theme has templates/product.probe.liquid: the product's template_suffix is 'probe'
```

**Theme overlays.** `ThemeInput.base` lays a theme over another: a file in the overlay's `files` replaces the base's file at the same path, every other file comes from the base, and the base is parsed once for every theme laid over it, so a theme that adds or edits a few sections of a large one pays only for its own files (see [Safety](#safety) for what not to edit).

```js
const base = { files: themeFiles }
const draft = { base, files: { 'sections/hero.liquid': '<h1>{{ section.settings.title }}</h1>{% schema %}{ "name": "Hero", "settings": [{ "type": "text", "id": "title", "default": "Hello" }] }{% endschema %}' } }
await renderPage({ theme: draft, templateName: 'index', data })
```

**`content_for_header`.** Besides the page's `hreflang` links in every market and language and the `{% stylesheet %}` and `{% javascript %}` tags' bodies (linked as compiled files with `compiledAssetsUrl`, inlined without it), it defines the `window.Shopify` globals themes read: `Shopify.shop`, `Shopify.locale`, `Shopify.currency` (`{ active, rate }`), `Shopify.country`, `Shopify.designMode`, `Shopify.routes.root`, the view's root with a trailing slash (`/`, `/fr-ca/`), which theme scripts put before the Ajax addresses they call, and `Shopify.analytics`, the [customer events API](https://shopify.dev/docs/api/web-pixels-api/emitting-data): `publish(name, data, customData)` keeps the event in `Shopify.analytics.events` and answers `true`, and `visitor(data, options)` answers whether it was given data. No event is sent anywhere.

```js
// in a theme script on a page under /fr-ca:
fetch(Shopify.routes.root + 'cart/add.js', { method: 'POST', body: formData }) // posts to /fr-ca/cart/add.js
Shopify.analytics.publish('size_chart_opened', { product: 'hoodie' }) // true; the event is in Shopify.analytics.events
```

### Services

The package never fetches anything and names no host of its own: the only literal hosts are the video players' embed URLs that `external_video_url` and `external_video_tag` write (`https://www.youtube.com/embed/` and `https://player.vimeo.com/video/`), and the SVG namespace in the default artwork is not a host. URLs, artwork, fonts and the clock come from `services`, which both `renderPage` and `createShopifyLiquid` accept; every one has a host-free default, and the defaults are Debutify's stand-ins, not Shopify's output, except two: the payment icons and the font library are Shopify's own (`paymentTypeSvg` and `fontInfo` below; the fonts `fontInfo` returns are frozen and shared, see its row). `defaultServices` is frozen: to change a service, pass your own function in the `services` option, which is merged over the defaults for that call.

### The render report

Every render returns a `report` with `unknownTags`, `unknownFilters` and `stubbedFilters` (name, count, files), `missing` (templates, layouts, sections, section groups, blocks, snippets, translations and resources the theme named but the theme or data did not have), `unsupported` (features and inputs the package could not render faithfully, such as app blocks), `errors` (inline errors with file and line), `sections` (each section's id, type, location, status and time) and `timing`.

A `missing` entry's `kind` and an `unsupported` entry's `feature` are snake_case values of the exported types `MissingKind` (`template`, `layout`, `section`, `section_group`, `block`, `snippet`, `translation`, `resource`) and `UnsupportedFeature` (`invalid_setting`, `unsafe_url`, `unsafe_key`, `app_block`, `blocks`, `section_group`, `wrapper` and the rest, including the name of a filter that could not use its input, such as `color_darken`), so a caller can switch on them. Report strings are plain text, not HTML: the names and files of `unknownTags`, `unknownFilters` and `stubbedFilters`, the names of `missing` and the details of `unsupported` have `<` and `>` removed but can still hold quotes and ampersands, and the messages of `errors` and the entries of `sections` are not filtered at all, so escape every report string when you show it as HTML.

An unknown filter returns its input and an unknown tag renders nothing, so one gap never blanks a section. `unknownTags: 'error'`, an option of `createShopifyLiquid`, `renderPage` and `renderSection`, makes an unknown tag a parse error instead (`Unknown tag 'name'`); under `renderPage` the file that holds it then fails like any file that does not parse. shopify.dev documents neither behaviour nor the text of an inline error (`Liquid error (sections/header line 12): …`); they follow the recordings in Shopify's [liquid-spec](https://github.com/Shopify/liquid-spec).

### Filter status

`shopifyFilterRegistry()` lists every filter in Shopify's [theme-liquid-docs](https://github.com/Shopify/theme-liquid-docs) with a status: `exact` (matches output recorded from Shopify), `approx` (implemented from shopify.dev, not yet matched against Shopify), `stub` (documented but not implemented: renders nothing and is reported) or `engine` (a standard Liquid filter provided by the engine). This release has 154 filters: 50 `engine`, 63 `approx`, 34 `stub`, 7 `exact` (`payment_type_svg_tag`, matched against `probe-payment-icons`, and `md5`, `preload_tag`, `inline_asset_content`, `structured_data`, `standard_event_data` and `money_amount`, matched against the parity store's recordings of Horizon and Dawn); a filter becomes `exact` only after it matches output recorded from a Shopify store. The parity probes record `money` and `money_with_currency` in three currencies, and the engine matches them (see [Behaviours confirmed on Shopify](#behaviours-confirmed-on-shopify)), but both stay `approx` until the inputs listed for them under [Behaviours still to confirm on Shopify](#behaviours-still-to-confirm-on-shopify) (nil, strings, fractions of a cent, negative amounts) are compared too; `json` stays `approx` because its escapes are Debutify's choice. `shopifyFilterRegistry()` returns new entries on every call, so editing them changes nothing. `shopifyFilterRegistry().filter((filter) => filter.status === 'stub')` lists the stubs, among them `sha1`, `hmac_sha1`, `base64_url_safe_encode`, `base64_url_safe_decode`, `asset_img_url`, `file_url` and `payment_type_img_url`.

### Safety

Theme files come only from the `files` map: no file-system access and no `require`. A theme may be laid over another with `ThemeInput.base`: a file in its `files` replaces the base's file at the same path and every other file comes from the base, which `compileTheme` parses once for every theme laid over it; give each version of a theme its own object, and do not edit the files of a base after a theme was compiled over it. The preset turns on `ownPropertyOnly` and sets `parseLimit` (10,000,000 characters per file), `renderLimit` (2,000 ms per render) and `memoryLimit` (100,000,000 of LiquidJS's allocation units per render); `createShopifyLiquid` takes all three and `unknownTags` (`ShopifyLiquidOptions`), `renderPage` and `renderSection` take the same four (`RenderPageOptions`, which `RenderSectionOptions` extends), and `compileTheme` takes `parseLimit` and `unknownTags`, so callers may lower the limits at each of them; `renderLiquid` takes none, because it renders with the engine you give it. `SHOPIFY_DEFAULT_LIMITS` is frozen: to change a limit, pass it as an option of the call. A render that runs past `renderLimit` or `memoryLimit` rejects instead of returning a page (`template render limit exceeded`, `memory alloc limit exceeded`); test what you catch with `isLimitError(err)`, as the options section above describes. These limits are cooperative, not isolation: render themes you did not write in a worker thread or child process with memory limits and a kill timeout, as LiquidJS's [security model](https://liquidjs.com/tutorials/security-model.html) advises.

Setting values are treated as untrusted by default, which is different from Shopify. On shopify.dev's [input settings](https://shopify.dev/docs/storefronts/themes/architecture/settings/input-settings) page, a `liquid` setting accepts "HTML and limited Liquid markup" that Shopify renders, and an `html` setting has only `<html>`, `<head>` and `<body>` removed; the page says nothing about sanitising them, so Shopify in effect trusts the merchant who writes them. Debutify's preset is built for settings that an AI model or a user wrote, so it does the opposite until you opt in:

- A `liquid` setting prints as escaped text, so `{{ shop.name }}` and markup in it show up literally.
- An `html` setting passes an allowlist sanitiser that keeps formatting markup and links and drops scripts, styles, frames, forms, event handlers, inline styles and every URL scheme but `http`, `https`, `mailto` and `tel`. It is not a general-purpose sanitiser; it only makes setting values safe to print. Any other text setting (`text`, `textarea`) that contains `<` goes through the same sanitiser, and plain text prints byte for byte as stored.
- `richtext` and `inline_richtext` settings are always sanitised, whichever mode you choose.
- [Dynamic sources](https://shopify.dev/docs/storefronts/themes/architecture/settings/dynamic-sources) in section and block setting values (`{{ closest.product.title }}`) resolve in both modes, because Shopify stores them in its own templates and presets: only a whole `{{ <object path> }}` from an object the page lists resolves, never a filter, a tag or other Liquid (that stays text and is reported), and never a name every JavaScript object has (`constructor`, `__proto__`). The text around a reference is sanitised as its type's text is; the value goes in as the store data holds it (a product's description keeps its markup), escaped where it lands inside a tag, and `StoreData` is printed as given, as everywhere else. An `href` or `src` that a reference fills in `richtext` or `inline_richtext` is held to the sanitiser's schemes once filled, so a `javascript:` URL in a metafield is dropped (feature `unsafe_url`) as one typed into the setting is.
- Every other setting type is held to the form shopify.dev documents for it, because Shopify's editor writes only those forms. A `url` or `video_url` with a quote, angle bracket, backtick, whitespace or control character, with a character reference to a quote or a number (`&#39;`, `&quot;`, `&apos;`), or with a scheme other than `http`, `https`, `mailto` and `tel`, is dropped (relative paths, `/…`, `#…` and `shopify://…` pass). A `text_alignment` must hold one of its three values, and a `select` or `radio` one of its options, except that a saved value that is no longer an option and is a plain token (letters, digits, `-` and `_`) is kept, as the parity store prints a saved `none` for a select whose options are `vertical` and `horizontal`. A `range` and a `number` must be finite numbers, and a `range` is clamped to its `min` and `max`. A `checkbox` must be a boolean, and one that is unset with no `default` reads `false`, as shopify.dev says. A `color` must be hex, `rgb()` or `hsl()` (alpha forms included), so a named colour such as `red` is rejected, and a `color_background` must be a colour or a plain gradient: `linear-gradient`, `radial-gradient`, `conic-gradient` and their `repeating-` forms around colours, so a value that calls any other function, such as `url()`, is rejected. An `image_picker` given as data needs a URL-shaped `src` (held to the same rules as a `url`) and numeric `width`, `height`, `id` and `focal_point`, and an `alt` whose apostrophes become typographic ones (`Women's dress` reads `Women’s dress`, which cannot end a single-quoted attribute); an `alt` that still has a double quote, angle bracket, backtick or control character is dropped, and the image stays. A colour scheme's id may hold only letters, digits, `-` and `_`. A `url` setting stored as a `shopify://` link to a page of the shop (`shopify://collections/all`) takes the view's prefix (`/fr-ca/collections/all`), as the parity store prints it; a path or an address written out stays as written. A `metaobject` or `metaobject_list` setting holds no metaobject here, so a string stored in it follows the text rule above.
- In untrusted mode the JSON that places sections and blocks is held to the same rule, because themes print `section.id`, `block.id` and `block.type` in ids, class names, attributes and `<style>`. A section key, a block key and a block `type` may hold only letters, digits, `-` and `_` (Shopify's own are of that form), a block `type` may also be `@app` or the `shopify://apps/…/blocks/…/…` form of an app block, and a section group's `type` may also hold `.` (`custom.<name>`). Anything else is skipped (a group `type` falls back to the group's name) and reported under the feature `unsafe_key` without the key. A template `wrapper` with an event-handler attribute (a name starting with `on`, in any case) or a `style` attribute is not applied, so the page renders without a wrapper, and is reported under the feature `wrapper`; `parseWrapper(spec, trusted)` takes `true` as its second argument to accept them, which is what trusted mode passes. In either mode the value of a wrapper's `[name=value]` attribute is escaped, so `&`, `<`, `>`, `"` and `'` are written as `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&#39;`.
- A rejected value falls back to the setting's default (or to what an unset setting of that type reads) and is listed in `report.unsupported` under the feature `invalid_setting`, `unsafe_url`, `unsafe_key` or `color_scheme`; the entry never contains the rejected value. Stored keys that are not declared and carry a quote, angle bracket, backtick or control character are dropped the same way (feature `unsafe_key`). A resource setting whose handle names nothing is listed in `report.missing` by its setting (`product of setting featured`), not by the handle, an unknown `font_picker` font is reported without its handle, and a missing section or block `type` shows as `(unsafe name)` unless it is made of letters, digits and `. _ - / : @`, because the report may be shown as HTML.
- `json`, `jsonify` and `inspect` always write `/` as `\/` and `<`, `>`, `&`, U+2028 and U+2029 as `\uXXXX` escapes, whichever mode you choose, so a stored value or key cannot end a `<script type="application/json">` block; the escaped text parses to the same JSON. `\/` is what Shopify prints (it is recorded on liquid-spec's Dawn pages); shopify.dev says nothing about escaping and no recording holds the other characters, so those escapes are Debutify's choice.

To opt into trusted mode, pass `trustLiquidSettings: true` for `liquid` settings and `trustHtmlSettings: true` for every other rule above (sanitising, the form checks, the dropped keys, the key rule for sections and blocks, the `wrapper` rule) to `renderPage` or `renderSection`. Do that only for themes whose author you trust; the `json` escapes stay on. Trusted `liquid` settings render with the scope of the place where they print, to at most five levels of nesting; shopify.dev says Shopify withholds `section`, `settings` and a few tags from them, and this package does not. A trusted `html` setting loses its `<html>`, `<head>` and `<body>` tags, as shopify.dev says, and prints the rest as stored: shopify.dev says Shopify closes unclosed tags when the setting is saved, and this package does not, so a tag left open stays open in the page.

Trusted mode is set only on `renderPage` and `renderSection`, which build the settings objects; `createShopifyLiquid` and `renderLiquid` take no trust options.

Untrusted mode keeps setting values out of script and markup contexts, but a few things stay with the caller. A text-like setting prints byte for byte, so it can still close an attribute that a theme prints it into without `| escape` (`class="{{ section.settings.cls }}"` with `x" onmouseover="alert(1)`), and it is a `javascript:` link wherever a theme uses a text setting as a URL (`href="{{ section.settings.label_link }}"`, `link_to`); `json` output inside an attribute needs `| escape` too, because it escapes `<`, `>`, `&` and `/` for a script block and leaves quotes as they are. `StoreData` and `request` values are printed exactly as given, so sanitise them yourself when you do not trust them. Serve previews from a sandboxed origin, and run a theme check for unescaped text settings in attributes and for text settings used as URLs on any theme you give untrusted settings.

### Conformance

Shopify's liquid-spec runs in CI on the Shopify preset, including the recordings of Shopify's Dawn theme. The numbers, what the build gates on, the known gaps and the [behaviours still to confirm on Shopify](#behaviours-still-to-confirm-on-shopify) follow under [Shopify compatibility](#shopify-compatibility).

## Shopify compatibility

On the Shopify preset (`createShopifyLiquid`), 4015 of the 4585 specs in Shopify's [liquid-spec](https://github.com/Shopify/liquid-spec) (commit 84bf25e) pass (87.6%), and 13 of the 26 specs recorded from Shopify's Dawn theme pass (the other 13 need Dawn's snippets, see Known gaps). CI runs them on every push to `master` and on every pull request, and gates on the per-spec baseline in `spec/liquid-spec/baseline.json`: a spec that passed must keep passing, and the pass count may not drop.

The figures count the specs the adapter runs, not every spec in the gem. `spec/liquid-spec/adapter.rb` skips the specs that need Ruby objects or bytes that JSON cannot carry (Ruby drops and types, drop class names, randomness, binary data, template factories, `self` shadowing the environment), the range resource limits and the strict2 blank-body errors, and five Shopify feature groups (`shopify_includes`, `shopify_blank`, `shopify_error_handling`, `shopify_error_format`, `shopify_string_access`) stay switched off because each has failing specs. liquid-spec records its specs from Ruby Liquid without bug-compatible trimming, so `spec/liquid-spec/server.mjs` runs the preset with `bugCompatibleWhitespaceTrimming: false`; the Dawn suite compares whitespace-normalised HTML, so this changes no Dawn result, and the preset's own tests cover the bug-compatible mode. Most of the other known failures are differences in the core engine inherited from LiquidJS: parser edge cases and error texts, `for` loop `limit` and `offset` permutations, and Ruby `inspect` text.

The storefront objects are compared with Debutify's parity store, a Shopify development store seeded with `storefrontSampleData` (`test/storefront/fixtures`, cut from its recordings): 70 probe fixtures, templates that print the objects of a page as JSON, and the Ajax answers recorded beside them. `test/storefront/all-probes.spec.ts` renders the last request of every probe fixture and expects the recorded body, except the keys listed below under Known gaps, each with its fixture, where it pins the engine's own value instead; values the parity store makes at random or at seed time (ids, keys and timestamps, listed with their reasons in `VOLATILE` in `test/storefront/expect-probe.ts`) are masked on both sides.

### Known gaps

Shopify features the package does not have yet, most of them seen as failing liquid-spec specs, and the parity store's values the engine cannot make from the store data:

- `base64_url_safe_encode` and `base64_url_safe_decode` are stubs (15 specs), as are `sha1` and `hmac_sha1`.
- `date` and `time_tag` lack some strftime directives: `%F %D %T %R %r %v` print the directive, `%V %G %g` (ISO week) are not expanded, and `%c %x %X` print locale text where Ruby prints `Mon Jun 15 14:30:45 2020`, `06/15/20` and `14:30:45`; a string's own offset (`-0400`) is dropped, so `%z` prints `+0000`, and an empty format does not print Ruby's default (`2020-06-15 14:30:45`).
- `render … for items` without `as` loops but does not bind the partial's name (`render … for items as name` does), `include … for` does not loop over the collection, `include … with value as name` does not bind `name`, and an `include … with` followed by a named argument (`{% include 'font' with multiplier: 1.5 %}`) binds differently from Shopify's lax parser.
- `string.first` and `string.last` print nothing (shopify.dev does not pin them; liquid-spec expects them to work).
- Bracket access `a['size']` returns the length, where Shopify reads nil.
- Ruby's comparison errors (`comparison of String with 1 failed`) are not reproduced.
- `tablerow` differs from Shopify on a string collection (one cell, `limit` and `offset` ignored), on a `limit` that is not a number (Shopify raises `invalid integer`) and on `break` and `continue` inside it.
- A recursive `render` or `include` runs to `renderLimit` (`template render limit exceeded`) instead of stopping at `Nesting too deep`.
- `ifchanged` is not implemented and is reported as an unknown tag.
- Dawn's snippet files are not vendored, because Dawn's licence limits use to building Shopify themes, so the 13 Dawn specs that render them cannot pass.
- Search results are not ranked by Shopify's relevance, which the store data does not carry: they come in store order (products, pages, articles). The parity store ranks `probe-search-type-product` as gray-leather-sneakers, canvas-sneakers, high-top-sneakers, white-leather-sneakers, and `probe-search-shirt` lists the article liquidpeak-450 before new-line-of-tennis-products where `probe-search-prefix` lists them the other way round; no rule of plain matching gives these orders, so the `results` of `probe-search-type-product` and `probe-search-shirt` are compared as sets.
- Predictive search and product recommendations do not match Shopify's index and sampling. For `q=ca` the parity store finds the `hoodie` product first and `canvas-sneakers` second (fixture `probe-predictive-prefix`, whose `products` are left out), though nothing in the dataset for the hoodie, or for `soft-cotton-hoodie-in-clay`, which has the same variants and is not found, holds a word that starts "ca", so the engine finds `canvas-sneakers` alone; and the parity store samples related products at random from the collections the product is in (fixtures `ajax-recommendations-json` and `probe-recommendations-related` give different products for the same request, sharing two of four, and all eight are in the dataset's `tops` collection) and has the `hoodie` in collections the dataset does not list, so the engine's related products for it are `hoodie-old` and the hoodies of its type (the `products` of `probe-recommendations-related` are left out). The shape of both answers is compared with the fixtures, with the dataset put as the recording says for the recommendations.
- `routes.account_login_url` is `<prefix>/account/login`, where the parity store, which uses new customer accounts, prints Shopify's login address on its own domain (`https://<store>.myshopify.com/customer_authentication/redirect?locale=en&region_country=US`, fixtures `probe-page-home`, `probe-page-en-ca`, `probe-page-en-eu`, `probe-page-fr-ca` and `probe-page-fr-eu`, where the key is left out). The store data does not say which kind of customer accounts a store has, and customer accounts are out of scope; the engine's customer templates are the classic ones.
- Timestamps print as the store data gives them: Shopify prints a product's `created_at` and `published_at` with the shop's UTC offset (`2026-10-15T13:04:43-04:00`, fixture `probe-product-default`), and the store data has times in UTC (`2026-08-14T15:57:54Z`) and no shop time zone. The parity store's own values are also the moment it was seeded, so the comparison masks them (`VOLATILE`).
- Values Shopify makes for each store or request are the engine's own: a selling plan group's `id` is the data's, where Shopify prints a checksum of 40 hex digits; a discount application's `key` is a UUID-shaped hash and its `created_at` the epoch, where Shopify makes a UUID and the moment of the request; a cart line's `key` hashes what the engine chooses (see the cart line under Behaviours still to confirm); and the cart `token` and the `id` of an added line in a cart change are the caller's or the engine's. The comparison masks these (`VOLATILE`).
- A shipping rate's `markup` in a market with another currency is `"0.00"` where Shopify prints the printed price less the rate's base price converted at its live exchange rate (`-0.17` for the Canadian Standard rate, `1.15` for the European International rate: fixtures `ajax-shipping-rates-en-ca` and `ajax-shipping-rates-en-eu`). About 1.4175 for CAD and 0.89 for EUR fit every recorded point to a cent; the dataset holds no live rate and it changes daily, so the engine does not compute it and the tests mask the field. The prices themselves match.
- The wording of form errors and the names `form.errors.translated_fields` gives them are not recorded (the parity store's bot challenge answers every scripted contact post with 403), so the messages are the caller's (`FormOutcome.errors`), a field's name comes from the theme's `shopify.<form type>.form.<field>` translation or is the field's own name capitalised, and `default_errors` prints nothing.

### Behaviours confirmed on Shopify

shopify.dev does not pin these outputs, or pins only part of them; each is what Debutify's parity store prints, and the engine prints the same. A line names where it was recorded: a fixture in this repository (`test/storefront/fixtures`, a name such as `probe-page-home` or `ajax-cart-session`), or, where no public fixture holds it, a parity recording (a scenario such as `page-home`, `page-product` or `page-contact`: a recording of the theme's whole page on the parity store, which is private and not in this repository because it holds the theme's markup). A behaviour that was not recorded, or is only assumed, is not listed here but under [Behaviours still to confirm on Shopify](#behaviours-still-to-confirm-on-shopify).

**Tags**

- [`form`](https://shopify.dev/docs/api/liquid/tags/form) of type `localization` prints the markup of the page's example with its action under the view's prefix (`/fr-eu/localization`), and returns to the page's whole address, its query included: `return_to` is `/pages/about?view=probe` on `/pages/about?view=probe` (fixtures `probe-page-home` and `probe-page-fr-eu`). The `&` between the parameters is written raw (scenario `page-collection-filtered`); a `"`, `<` or `>` in a path is percent-encoded. A browser reads a raw `&` followed by a legacy entity name that is neither followed by `=` nor by a letter or a digit as that entity (a parameter named `amp-x` comes back as `&-x`); Shopify's output has the same property, and it cannot end the attribute.
- [`form`](https://shopify.dev/docs/api/liquid/tags/form) given a `return_to` that is nil prints no `return_to` input: Horizon 4.3.0's localization form passes `return_to: back` with no `back` variable, and the parity store prints the form without one, neither the page's address nor an empty value (private parity recordings of Horizon, every page). An empty string is read the same way, which no recording holds.
- [`form`](https://shopify.dev/docs/api/liquid/tags/form) of type `contact` or `customer` posts to `/contact` anchored at the form's id (`/contact#ContactForm` for `id: 'ContactForm'`), as the parity store prints them (private parity recordings `page-contact`, `page-home` and `page-page`, not fixtures: the ids `ContactForm`, `ContactFooter` and `NewsletterForm`); without an `id` it anchors at `/contact#contact_form`, as shopify.dev's example prints it.
- `form` of type `product` with its product written with a quoted key prints nothing: `{% form 'product', all_products['hoodie'] %}{% endform %}`, with an empty body, captured on a page is `""` (fixtures `probe-page-*`). The rule the engine applies, that a product form whose object has any character outside a variable name with dots and square brackets prints nothing, is Debutify's inference from the character set of `FORM_FORMAT` in Shopify's [theme-check](https://github.com/Shopify/theme-check) (`lib/theme_check/tags.rb`), which agrees on the characters only: its pattern raises a syntax error for such an object, where the storefront printed nothing. Assign the product to a variable first (`{% assign hoodie = all_products['hoodie'] %}{% form 'product', hoodie %}`).
- [`paginate`](https://shopify.dev/docs/api/liquid/tags/paginate): a page past the last shows no items, with `current_page` the page asked for, `previous` the last page and no `next` (fixture `probe-collection-page-past`, page 9 of 8); `items` counts the collection's products after its filters (fixture `probe-collection-filter-tag`: 6); and the `next` and `previous` links keep the request's query with `page` set, the pairs ordered by name (fixtures `probe-collection-filter-combined`, `?filter.p.tag=accessories&filter.v.availability=1&page=2&sort_by=price-descending&view=probe`, and `probe-collection-page-2`, whose `previous` names page 1). A single page has no `parts`, and no `previous` or `next`: the parity store prints no pagination for Dawn 16.0.0's one page of collections, which prints it only `if paginate.parts.size > 0` (private parity recording `page-collections` of Dawn), and `pages` is 1 with `next` and `previous` null (fixture `probe-collection-suffix-filtered`). A page's part has its number as its `title` (a number, so `part.title == paginate.current_page` holds for the current page, as the parity store shows on page 2 of a collection: audit D1, finding E1), where [shopify.dev](https://shopify.dev/docs/api/liquid/objects/part) types it as a string. Not pinned: `part.title == '2'` is false (Ruby Liquid's `==` does not convert either), and `part.title | size` is 0 for a page's part, where Ruby's `Integer#size` gives 8.

**Translations and text**

- [`money`](https://shopify.dev/docs/api/liquid/filters/money) and [`money_with_currency`](https://shopify.dev/docs/api/liquid/filters/money_with_currency) print in the format of the view's currency: `$19.99` and `$19.99 USD` in the primary market, `$19.99` and `$19.99 CAD` in the Canadian one, and `€19,99` and `€19,99 EUR` in the European one, the code after a plain space (fixtures `probe-page-home`, `probe-page-en-ca` and `probe-page-fr-eu`).
- Content translations: a product's title and description, a collection's title, a page's title and content, a menu link's title and the shop's description print in the page's language when the store data has a translation, and the default language's text otherwise (fixture `probe-product-fr-eu`: the slides' English description on a French page); the shop's name is never translated (Shopify cannot translate it), and handles and URLs stay the same (fixtures `probe-page-fr-ca`, `probe-page-fr-eu` and `probe-product-fr-ca`).
- [`payment_type_svg_tag`](https://shopify.dev/docs/api/liquid/filters/payment_type_svg_tag) prints the file `app/assets/images/payment_icons/<type>.svg` of activemerchant/payment_icons, exactly as the repository holds it (a line break after `</svg>` where the file ends with one, an `<?xml version="1.0"?>` prolog where it starts with one, `paidy`), for the types of `db/payment_icons.yml` and for `bogus`, the one file outside it; an unknown type, the empty one and a capitalised `Visa` all print the `generic` icon, with nothing written for the type; a `class` lands right after `<svg`, after the prolog where there is one; the label of `mcb` keeps its entities (fixture `probe-payment-icons`, and the six types the store enables in the private recordings `page-home` and `ajax-cart-sections`).


**Fonts**

- Shopify's font library, from five font probes (fixtures `probe-fonts-library`, `probe-fonts-retired-1`, `-2`, `-3` and `-4`): each of the 2,109 handles shopify.dev lists as available has a `font` with its family (quoted when it holds anything but letters, digits and hyphens: `"SF Mono"`, `"New York"`), fallback families, weight (a string), style, `baseline_ratio`, `system?` and `variants` (the family's fonts in the order Shopify lists them: Assistant has seven weights and no italic, so `assistant_i4` is not a handle); `font_url` prints the file as `//<store>/cdn/fonts/<directory>/<file>?h1=…&hmac=…`, a signed address that names the store, where the engine prints `/fonts/<directory>/<file>` (the same two paths, `fonts.shopifycdn.com` serves them); a system font (`mono`, `serif`, `sans_serif_n4`, `system_ui_n4` and the other eight) prints the empty string for `font_url` in both formats. The 1,342 retired handles of shopify.dev's "Deprecated fonts" render the font that page names in its place (1,339 of them, with the file of a library font: `harmonia_sans_n4` is `poppins_n4`, `helvetica_n3` the system `sans_serif_n4`, `sans-serif` the system `system_ui_n4`), and `memphis_i3`, `memphis_i5` and `memphis_i7` raise `Font not found`, so they are unknown here.

**Markets**

- Under a locale prefix every route but `account_login_url` (see Known gaps) and every resource URL starts with the prefix, and `routes.root_url`, `request.locale.root_url` and each language's `root_url` are the bare prefix with no trailing slash (`/fr-ca`), or `/` with none (fixtures `probe-page-fr-ca` and `probe-page-home`). `request.locale` is the language the page is shown in.
- [`localization`](https://shopify.dev/docs/api/liquid/objects/localization): a market's default country is the one with the lowest ISO code (`DE` for the Europe market, whose data lists France first; fixture `probe-page-fr-eu`); country names are in the page's language (`Allemagne`, `États-Unis`) and `available_countries` is sorted by them; and a language's `name` is in the page's language (`français` on a French page, fixture `probe-page-fr-ca`), where shopify.dev says the store's primary language.
- `shop.enabled_currencies` is sorted by ISO code (`CAD`, `EUR`, `USD`, fixture `probe-page-home`), and `shop.published_locales` lists the languages of the view's market with the view's root URLs (fixtures `probe-page-en-ca`, `en` at `/en-ca` and `fr` at `/fr-ca`, and `probe-page-home`, `en` at `/` alone).
- Prices in another market's currency are the shop's at the market's rate, rounded up: CAD to whole units (90.00 USD at 1.35 is 121.50 and prints 122.00, fixture `probe-product-en-ca`) and EUR to `.95` (25.00 USD at 0.92 is 23.00 and prints 23.95, fixture `probe-product-en-eu`; 10.00 USD is 9.20 and prints 9.95, fixture `probe-product-en-eu-workout-shirt`), where the help centre's [exchange rates](https://help.shopify.com/en/manual/international/pricing/exchange-rates) example rounds 8.81 EUR to 8.85. A market with an EEA country hides compare-at prices: `compare_at_price` is nil on the product and its variants, and the product's `compare_at_price_min` and `compare_at_price_max` are 0 (fixture `probe-product-en-eu-hoodie`).

**Store data**

- [`product.compare_at_price`](https://shopify.dev/docs/api/liquid/objects/product) is the lowest compare-at price of the variants that have one (fixture `probe-product-default`: 110.00, one variant of twenty) and nil when none has one (fixtures `probe-product-in-collection` and `probe-product-plans`), so dividing by it raises `divided by 0`; `first_available_variant` is nil when every variant is sold out (fixture `probe-product-en-eu-leggings`).
- `position` on product [images](https://shopify.dev/docs/api/liquid/objects/image) and [media](https://shopify.dev/docs/api/liquid/objects/media) counts from 1 (fixture `probe-product-default`: the hoodie's eight media print 1 to 8, and its sixth image, the first variant's, 6).
- `product | json` prints its own shape, not the `/products/<handle>.js` answer: `options` as the option names, no `url`, `content` last, and variants without `quantity_price_breaks` that end with `quantity_rule` (fixture `probe-product-default`). A product's `url` on `/collections/<collection>/products/<product>` is the plain `/products/<product>` (fixture `probe-product-in-collection`).
- [Collections](https://shopify.dev/docs/api/liquid/objects/collection): `sort_by` is `''` when the request names none, and `sort_options` lists `Featured`, `Most relevant`, `Best selling`, then the title, price and date orders (fixture `probe-collection-all`). A descending order is the exact reverse of the ascending one, ties included (fixtures `probe-collection-sort-price-ascending` and `-descending`: the two 25.00 products come slides then clear-sunnies, and the other way round). `manual` keeps the collection's order, and on `all`, `vendors` and `types`, which have none, is the title order, which is also `all`'s default (fixtures `probe-collection-sort-manual` and `probe-collection-all`). With no sales, best selling lists the catalogue's newest products first (fixtures `probe-collection-best-selling` and `probe-collection-sort-best-selling`).
- `collection.products` is in the collection's default order wherever it is read, not only on the collection page: `collections['all'].products` by title (the parity store's header suggestions and empty cart; private parity recordings `page-home` and `page-cart-empty`, not fixtures), a collection with `sort_order` in that order; the collection page's own `sort_by`, `manual` included, starts from the store data's order, so its output is unchanged (the `probe-collection-*` fixtures); the list is sorted when first read and kept. `{% for c in collections %}` lists the collections alphabetically by title, also in a store whose data lists them otherwise ([`collections`](https://shopify.dev/docs/api/liquid/objects/collections) shows its example so; private parity recording `page-collections`, not a fixture); the Home page collection (`frontpage`) is in the sample data, not made by the engine, because a store can delete it. A collection whose `sort_order` is none of the sort values (`manual`, `best-selling`, `title-ascending`, `title-descending`, `price-ascending`, `price-descending`, `created-ascending`, `created-descending`) is in the data's order, as `manual`, and its `default_sort_by` is `manual`: unrecorded, and no report says so, because a store is built without one. `blog.articles` lists the newest article first (private parity recording `page-blog`, not a fixture), while the search and the predictive search keep the data's order for results that tie (fixture `probe-search-prefix`).
- A product's own images and media read the product's title as their `alt` when they have none (private parity recordings `page-product` and `page-collections`, not fixtures), but `product | json` and `/products/<handle>.js` print `null` (fixtures `probe-product-default` and `ajax-product-js`), `media.preview_image.alt` is empty, and the card of a collection filtered by variant shows the matching variant's media as that bare image, whose `alt` is nil (private parity recordings `page-product` and `page-collection-filtered`; Horizon's card passes `alt: media.alt` and the store prints no `alt` attribute). A menu link to `/collections` is active only on the collections page itself, where a link to a blog or a collection is also active on the pages below it (private parity recordings `page-collection` and `page-article`). `product.variants | json`, and a variant on its own, print as the variants of `product | json` (private parity recording `page-product`).

**Page assembly**

- A page gets Shopify's store element right before every `<shopify-account` element the theme prints: `<shopify-store store-domain="<origin>" country="<country>" language="<language>"></shopify-store>` and a line break, the theme's indentation left before it (private parity recordings of Horizon 4.3.0 and Dawn 16.0.0, every page: `country="US" language="en"`, `country="CA" language="fr"` under `/fr-ca`, `country="DE" language="en"` under `/en-eu`). `store-domain` is the origin the page is served at (`request.origin`), which is the parity store's own address on its preview and `https://kith.com` on the live store kith.com, whose `Shopify.shop` is `kithnyc.myshopify.com`. [shopify.dev](https://shopify.dev/docs/api/storefront-web-components/components/shopify-store) documents the element and calls `store-domain` "the myshopify.com domain of the store", and does not say that Shopify adds it. Debutify's, not pinned: `language` is the page's locale code as it is, recorded only for two-letter languages (`en`, `fr`, and `ja` on kith's Japanese shop), so a regional locale such as `pt-BR` prints `pt-BR`, where Shopify might print another form; an account element inside a script, a style, a textarea or a comment gets none, every account element gets its own (the recorded pages have one each), and `renderSection` adds none.
- `content_for_header` links the theme's compiled `{% stylesheet %}` and `{% javascript %}` files when `RenderPageOptions.compiledAssetsUrl` says where they are served, as the `/storefront` entry does: `<link rel="stylesheet" media="screen" href="<url>styles.css?v=<version>">` on every page of a theme with a stylesheet in a section, block or snippet, then `<script id="sections-script" data-sections="<sections>" defer="defer" src="<url>scripts.js?v=<version>"></script>` naming the page's sections that have a `{% javascript %}` (private parity recordings of Horizon 4.3.0, every page, and `data-sections="main-collection"` on its collection pages; Dawn 16.0.0 and the private theme, `data-sections="header"` on every page). `styles.css` holds every stylesheet of the theme whatever the page renders (the parity store links one address on every page, and its file, read through its source map, holds the `password` section's styles), in the parity store's form: `/* SHOPIFY_STYLESHEETS_VERSION: 1.0 */`, then the sections, the blocks and the snippets, each group under `/* CSS from section stylesheet tags */` and in file name order, each body trimmed between `/* START_SECTION:<name> (INDEX:<n>) */` and `/* END_SECTION:<name> */`, `<n>` counting the `.liquid` files of the three folders. `scripts.js` holds every section's javascript, each run only when `data-sections` names its section, in a `try` that logs its error, in the parity store's form. Both files' text is, byte for byte, the source the parity store's source maps hold: Horizon 4.3.0's `styles.css` (154 files) and `scripts.js`, and the `scripts.js` of Dawn 16.0.0 and of the private theme. Debutify's, not pinned: the files are served as written, where Shopify serves them minified; the version is a hash of the file, where Shopify's is a number of its own; [shopify.dev](https://shopify.dev/docs/storefronts/themes/best-practices/javascript-and-stylesheet-tags)'s subset of the styles to each page's render tree is not served: the page links the whole file, as the parity store's pages do, and Shopify also answers `styles.css?v=<version>&subset=<sections>` with a part of it, which a browser asks for on its own (the whole file is advertised as a compression dictionary for them, `use-as-dictionary`), where this storefront answers a `subset` query with the whole file; a stylesheet of a layout or a template stays inlined; and the javascript of blocks and snippets, which Shopify compiles into `block-scripts.js` and `snippet-scripts.js` that no recording shows, stays inlined in a `DOMContentLoaded` script, each body in a `try` that logs its error, as the compiled `scripts.js` runs each section's, so one that throws does not stop the others. Without `compiledAssetsUrl`, or with `''` (a page rendered with no server behind it, such as a design tool's) every stylesheet and javascript body the page rendered is inlined, as in 1.2.0.

### Behaviours still to confirm on Shopify

shopify.dev does not pin these outputs, or pins only part of the filter, tag or object a line belongs to, and no parity fixture records them, so the package follows the closest documented behaviour or Shopify Liquid's own tests and the filter stays `approx` until it is compared with a Shopify store. Each line names the part that stays open, and links the shopify.dev page where there is one; what the parity store has settled is under [Behaviours confirmed on Shopify](#behaviours-confirmed-on-shopify).

**Tags**

- [`form`](https://shopify.dev/docs/api/liquid/tags/form): the position of extra attributes beyond the documented example; the `customer_address` form for an existing address (the page lists its fields, `address1` to `zip`, and this engine fills them from the address, HTML-escaped like a posted value, a posted value winning; whether Shopify does is not recorded, and a nil address, as `customer.new_address` is here, fills none); `form.id` for form types other than `customer_address`; for a `product` form whose object has a quoted key, whether its content is dropped too (it is here), and for one whose object has an unquoted key (`all_products[handle]`) or is nil or missing, what Shopify prints (here a form, with `id="product_form_"` for a nil object); a form of another type with such an object, which reads the whole expression here; the order and encoding of several query pairs in a `localization` form's `return_to` (the fixtures hold one; a `+` in a value prints `%20` here); the translation key a field's name in `form.errors.translated_fields` comes from (`shopify.<form type>.form.<field>`, Debutify's).
- [`render`](https://shopify.dev/docs/api/liquid/tags/render) given a block (`{% render block %}`, `{% for child in block.blocks %}{% render child %}{% endfor %}`): a theme block renders as `content_for` renders it, in its wrapper unless its schema says `"tag": null` (shopify.dev documents `{% render block %}` only for app blocks, so the theme-block case is Debutify's reading); an app block prints nothing and is reported; parameters after a block are not passed. Any other value that is not a string (a number, an object) is a render error, `render needs a snippet name or a block, not a number`, in Debutify's words.
- `form` of type `product` inside a section: after `product-id` it adds `<input type="hidden" name="section-id" value="<the section's id>" />`, which Shopify's Dawn demo store prints today and no Dawn file prints, but which shopify.dev does not document (its example renders outside a section) and liquid-spec's older Dawn recording lacks, together with `product-id`.
- Blankness of Shopify's own `schema`, `javascript` and `stylesheet` tags, which print nothing where they stand: they count as blank here, so an `if` holding only one of them and whitespace prints nothing. Ruby Liquid does not have these tags, and shopify.dev does not say.
- [`form` object](https://shopify.dev/docs/api/liquid/objects/form): its example key is `password_needed?` while its property list says `password_needed`; only `password_needed` exists here.
- `form` of type `localization` or `currency`: an explicit `return_to` replaces the default instead of adding a second input (one that is nil or empty removes it, as recorded for Horizon); and the deprecated `currency` form returns to the page's whole address, query included, as `localization` does (only `localization` is recorded).
- [`paginate`](https://shopify.dev/docs/api/liquid/tags/paginate) and [`default_pagination`](https://shopify.dev/docs/api/liquid/filters/default_pagination): the default `window_size` (3) and the markup for windows wider than the documented example.
- `paginate` past the 25,000 item limit shows the last page it reaches.
- `paginate` reads `<name>_count` (`collection.products_count`) as the total, and takes a shorter array as the page already fetched.
- `paginate` clamps page sizes outside 1 to 250, and always uses `page` as the `page_param` key.
- [`javascript` and `stylesheet`](https://shopify.dev/docs/storefronts/themes/best-practices/javascript-and-stylesheet-tags): a second tag in one file is a syntax error on Shopify, and the first body wins silently here.

**Translations and text**

- Content translations of a collection's description and of an article's title, content and excerpt: they are translated like a product's, from the fields shopify.dev's `TranslatableResourceType` lists; no fixture or recording prints them.
- [`t`](https://shopify.dev/docs/api/liquid/filters/translate): the text for a missing key (`translation missing: <locale>.<key>`, escaped), whether interpolated values are part of the translated content (here an `_html` key prints them as they are, so a template should escape data it passes in, and any other key escapes them with the rest), and a `zero` key winning for `count: 0` in every locale.
- Locale fallback ([storefront locale files](https://shopify.dev/docs/storefronts/themes/architecture/locales/storefront-locale-files)): a missing key falls back to the default locale and `fr-CA` to `fr`, and within a locale the locale file is searched before the section's schema `locales`.
- [`money`](https://shopify.dev/docs/api/liquid/filters/money): nil prints nothing, a boolean, array or hash prints nothing and is reported, a string is read like Ruby's `to_i` (`"abc"` is `$0.00`), a fraction of a cent is dropped and a negative amount prints `$-1.50`, all as in liquid-spec's reference filters.
- [`money_without_currency`](https://shopify.dev/docs/api/liquid/filters/money_without_currency) for a format with other placeholders (the first placeholder is used); the money formats of a market's currency when its data gives none: the currency's symbol before `{{amount}}` (`{{amount_with_comma_separator}}` for the euro) and its ISO code after a space, which the parity store prints for CAD and EUR and no fixture shows for any other currency.
- [`date`](https://shopify.dev/docs/api/liquid/filters/date) and [`time_tag`](https://shopify.dev/docs/api/liquid/filters/time_tag): a string without a zone is read as UTC, and the zone Shopify renders in is not pinned; a time in a skipped or repeated hour of a DST zone; a timezone argument, which the engine's `date` takes second and the page does not have.
- `date` and `time_tag`: every named format except `abbreviated_date`, and the text of the error for an unknown named format (Debutify's). Only `format: 'date'` is recorded (the parity store prints `February 7, 2023`, no padded day); the other formats that print a day take the same unpadded day, which is not pinned.
- `date` with a named `timezoneOffset` set through `engine` can print a time an hour off near a DST change when the machine itself is in a DST zone, an issue in the core LiquidJS date code.
- [`escape`](https://shopify.dev/docs/api/liquid/filters/escape) writes `&quot;` and `&#39;` as Ruby does, and `escape_once` counts named and decimal entities as already escaped.
- [`pluralize`](https://shopify.dev/docs/api/liquid/filters/pluralize) with a fractional or negative count reads it like Ruby's `to_i`, so `1.5` is singular; [`within`](https://shopify.dev/docs/api/liquid/filters/within) on a collection without a URL returns the URL unchanged.
- [`link_to`](https://shopify.dev/docs/api/liquid/filters/link_to) writes `title=""` and `rel="nofollow"` as the page's examples do for an external address, and no `rel` for an address without a scheme or host (the parity store prints the shop name linked to `/` as `<a href="/" title="">`); an absolute address on the shop's own host counts as external, which nothing pins.
- [`font_face`](https://shopify.dev/docs/api/liquid/filters/font_face) ends its rule with a line break, as the parity store prints it (the page cannot show one); a `fontFace` service writes the whole rule itself.
- [`handleize`](https://shopify.dev/docs/api/liquid/filters/handleize) on non-ASCII text and on characters the page's one example does not show follows liquid-spec's reference algorithm.
- `format_code` is not on shopify.dev; it groups a gift card code in fours.

**Media**

- [`image_tag`](https://shopify.dev/docs/api/liquid/filters/image_tag): the default `srcset` widths above 352; the section index after which images are lazy-loaded (after the third section of a location here); `preload: true` only stops the automatic `loading="lazy"`, because a string render cannot send a `Link` header.
- [`image_url`](https://shopify.dev/docs/api/liquid/filters/image_url) without a width or height returns the image's original URL with no size parameters, although the page's Caution says an error is returned; Dawn, Shopify's reference theme, prints the sizeless form as the last `srcset` candidate.
- `image_url: 'master'` (a positional size, read as omitted) and a nil or `0` `width:` or `height:` (also read as omitted).
- `image_url`, `img_url` and the `srcset` of `image_tag` print the default service's address without its protocol (`//host/files/a.jpg?width=450`), as the parity store does, so a theme's `image_url | prepend: "https:"` makes a valid address; a caller's own `imageUrl` service returns what it likes. An image object's `src` (and `product | json`) has no protocol either, where the Ajax answers (`/products/<handle>.js`, `/cart.js`, the suggest answer) print the data's own address, as the parity store does.
- `image_url` keeps the `width` and `height` the template asked for in the address, even past the image's own size (the CDN serves nothing larger than the original, and the parity store prints `width=1500` for an image 1024 wide), clamps them to 5760, scales an oversized two-sided request proportionally, clamps `quality` to 10 to 90, and sorts the query keys; `image_tag` writes its size and `srcset` from the URL's size, as the parity store prints Horizon's collection cards (width 3840 of a 1024 wide image).
- [`img_url`](https://shopify.dev/docs/api/liquid/filters/img_url): the default size (`small`, read from the page's no-argument example), an unknown or empty size (`small`), `original` and `master` as 1024x1024 (the page has one table row for both), and `crop`, `format` and `scale` changing nothing in the default service.
- [`video_tag`](https://shopify.dev/docs/api/liquid/filters/video_tag): `m3u8` sources when not looping, where `loading` goes, the section index for lazy loading, and the product-title fallback for `aria-label` (and for [`external_video_tag`](https://shopify.dev/docs/api/liquid/filters/external_video_tag)'s `title`), which reads the `product` variable in scope.
- `media_tag` on an image renders `image_tag` at the image's own width (1100 when it has none); the page has no image example.
- `escape` after [`image_tag`](https://shopify.dev/docs/api/liquid/filters/image_tag) leaves the tag as it is, as Shopify's Origin demo store shows for Dawn's `image_tag | escape` thumbnails and liquid-spec records for HTML-safe strings; whether Shopify's other tag filters (`stylesheet_tag`, `link_to`, `video_tag` and the rest) are HTML-safe too is not pinned, so `escape` still escapes theirs, and `escape_once` escapes `image_tag`'s.
- [`placeholder_svg_tag`](https://shopify.dev/docs/api/liquid/filters/placeholder_svg_tag) draws Debutify's own line art, not Shopify's, by design, since Shopify's artwork cannot be copied, in the markup the page's example shows (an `<svg>` with `xmlns` and a `viewBox` around one `<path>`, no background). Where the `<svg>` has `fill="none"` the `<path>` carries `fill="currentColor"`, and the drawing is scaled and centred in the viewBox. Not pinned, because no recording reaches these names and their frames are guessed from the family: `product-5`, `product-6` and `collection-4` to `collection-6` take the square, `lifestyle-1` the wide one, `hero-apparel-2` and `hero-apparel-3` the hero one, and every other `*-apparel-N` name (`product-apparel-1` to `product-apparel-4`, `collection-apparel-1` to `collection-apparel-3`, `blog-apparel-1` to `blog-apparel-3` and `detailed-apparel-1`) the 448 pixel tile, whose fixed `width` and `height` may change a layout where Shopify prints none for these names. Also not pinned: the colour of the names the page lists as colour illustrations (drawn as line art here), and a name the page does not list, which draws `image` here.
- [`shopify_asset_url`](https://shopify.dev/docs/api/liquid/filters/shopify_asset_url) prints the address its service gives (the filter is `approx`: it returns Shopify's CDN address of a global asset, which only Shopify can name, as its files are at hashed `/cdn/shopifycloud/storefront/assets/` addresses). The storefront answers it for the three files the three themes' gift card templates ask for, and they are stand-ins by design, as `placeholder_svg_tag`'s art is: the QR library is the MIT one Shopify's copy is, the card image and the wallet badge are Debutify's own drawings, not Shopify's or Apple's artwork. Any other global asset a theme names is a 404 at its address ([Shopify's global assets](#shopifys-global-assets)).
- [`payment_button`](https://shopify.dev/docs/api/liquid/filters/payment_button) prints the `<shopify-accelerated-checkout>` markup Shopify prints (the buyer's country, language and currency, a `{id, requiresShipping}` for every variant, the buyer consent text for a product sold with a selling plan), and `content_for_header` carries Shopify's `Shopify.PaymentButton` bootstrap. - Markets and languages ([multiple currencies and languages](https://shopify.dev/docs/storefronts/themes/markets/multiple-currencies-languages)): the `hreflang` links of `content_for_header` follow the parity store's recorded pages only (`x-default`, a tag for each language of the primary market, then each other market's countries in ISO order with each of its languages; none for a store of one market and one language; the query left out except a search's `q`); a currency's `name` is its ISO code unless the market data names it, a market's `id` is its place in the list and `unit_system` is `metric`; a currency rounds up only when its market data asks for rounding and the step is known (CAD and EUR, from the fixtures) or given, and the shop's own currency is not rounded; country and language names in another language come from the runtime's `Intl.DisplayNames`, and a runtime without that language uses the store data's names; content translations are found by the exact language code (`fr-CA` does not fall back to `fr`, as the theme's locale files do), and a menu's own title is not translated.
- [Selling plans](https://shopify.dev/docs/api/liquid/objects/selling_plan_group) come from `ProductData.selling_plan_groups`, with one allocation per plan on every variant the group offers (a group that offers none of the product's variants is not listed, as the [product](https://shopify.dev/docs/api/liquid/objects/product#product-selling_plan_groups) page words it). Not pinned: (1) a selected variant together with a selected plan (`?variant=…&selling_plan=…`): the variant's `selected_selling_plan_allocation` is taken to be its allocation for the plan, as the page ties it to the selected variant; the parity store was recorded with a plan and no variant only, where every variant's is nil. (2) `product.selected_or_first_available_selling_plan_allocation` with a variant chosen but no plan, or a plan that variant is not offered, is the first allocation of the first available variant, as the page words it (not the chosen variant's), and with `?selling_plan=71002` alone it is the first allocation (71001), which `probe-product-plan-selected` cannot tell from the selected plan's because 71001 is both. (3) A percentage price that is not a half minor unit is rounded to the nearest (halves up); the parity store was recorded with 2155.5, printed 2156, which half up, half even and rounding up all give. (4) A `price` adjustment is converted to a market's currency as the recorded fixed amount is, unrounded, and a market's price adjustment applies to both (the recorded market has none). (5) A plan with two price adjustments prices each from the variant's own price, and the allocation's `price` is the first. (6) An allocation's `compare_at_price` is the variant's price, also for a variant that has a compare-at price of its own. A plan's checkout charge is always 100 percent and `remaining_balance_charge_amount` 0, because the data holds no partial charge. A group has `selling_plan_selected` as the page names it, and no `selected`, which the parity store prints as nil.
- [`variant`](https://shopify.dev/docs/api/liquid/objects/variant) `unit_price`: rounded to the minor unit from the variant's price and its measurement, for the units of Shopify's Admin API (`ML`, `L`, `KG`, `FLOZ`, `ITEM`…) and nil for another; how Shopify rounds, and what `store_availabilities` holds on a variant that is neither selected nor the first available (nil here), are not pinned.
- [`metafield`](https://shopify.dev/docs/api/liquid/objects/metafield): what a metafield prints on its own (the stored value here, and `gid://shopify/<type>/<id>` for a reference) and the type read from a plain value are not pinned; what a typed value prints on its own is not pinned either: a `rating` prints its `rating` (`4.5`, which Dawn and our theme print before ` / {{ ...scale_max }}`), a `weight`, `volume` or `dimension` its value and unit (`500.0 mL`), and a `rich_text_field` the HTML of its tree (`<p>`, headings, lists, links, `<strong>`, `<em>`; text escaped, an unsafe link URL dropped); a list keeps only the items that resolve; a number field whose text is not a number gives nil, and an entry with an empty value is left out, as Shopify stores no empty value; a plain object of exactly `type` and `value`, whose `type` looks like a type name, is read as a typed `MetafieldData`, so untyped JSON of that shape needs another key.
- Reads that shopify.dev's object pages do not document print nothing: `shop.features`, `shop.checkout`, `collection.terms`, `collection.results_count`, `search.products_count`, `filter_value.alt`, `form.send_on` and `variant.instructions` (the three themes read them, and each falls back to its own default), and `section.shopify_attributes` (a block's is empty outside the theme editor, https://shopify.dev/docs/api/liquid/objects/block). What Shopify prints for them is not recorded.
- [`link`](https://shopify.dev/docs/api/liquid/objects/link) `handle`: a link whose title handleizes to nothing (only non-Latin letters, such as `ホーム`) gets `link-<position>`, and a handle a sibling link already has gets `-1`, `-2` and so on, so each id of a menu is its own; Shopify's handles for such titles are not recorded.
- [`collection`](https://shopify.dev/docs/api/liquid/objects/collection) `current_vendor` and `current_type` are the term HTML-escaped, so they print safely and `json` shows the entities (`&lt;`); the parity store recorded a plain term only (`mock.shop`).
- [`policy`](https://shopify.dev/docs/api/liquid/objects/policy): the titles of the policies other than the privacy policy (`Refund policy`, `Shipping policy`, `Terms of service`, `Cancellation policy`, `Contact information`, `Legal notice`) are Shopify's admin names, not recorded; a policy page's markup is the one the parity store prints for its privacy policy, and its layout rules are Debutify's own, not Shopify's stylesheet (the rules of the file Shopify links for the page are not copied): a container capped at `65ch` and centred and a centred title, which give the layout the recording shows but may differ from the file in margins and padding, inlined in the header rather than linked, since the file's address carries a hash that changes with Shopify's builds; what a policy prints on its own, and its `id` when the data gives none (nil here), are not pinned. A policy's body is the merchant's HTML and is printed as given, like a page's content and a product's description; only its title is escaped in the page's `h1`, and `page_title` carries it as given. The first entry of each policy type counts, and a type outside `PolicyData['type']` is ignored.
- [`product_option_value`](https://shopify.dev/docs/api/liquid/objects/product_option_value): an id the data does not give is the engine's (a hash of the product id, the option's position and the value), where Shopify numbers its own; a value prints, compares and goes through `json` as its name (the parity store prints our theme's `option.selected_value == value` as true, so a value compares as its name; what `json` prints is not recorded); with `?option_values=` naming some options only, the variant is the first available one with the named values (the parity store's answers to Dawn's section requests agree for one and two ids); and `?variant=` wins over `?option_values=` when both are given, also when the product has no such variant (then nothing is selected), which nothing records.
- Not modelled in store data: bundles (a cart line's `item_components` and `parent_relationship`), metafield types the store data cannot hold (`metaobject_reference`, `mixed_reference`, `file_reference` of a video or a generic file, `rich_text_field` beyond its JSON tree and the HTML it prints), the shop's time zone, the kind of customer accounts (the engine's are the classic ones), and Shopify Plus discount stacking.

**Theme runtime**

- Section and block ids: the [section object](https://shopify.dev/docs/api/liquid/objects/section) page says Shopify generates the ids of sections in JSON templates dynamically, and the [Section Rendering API](https://shopify.dev/docs/api/ajax/section-rendering) page gives only the examples `sections--1234__header` and `template--5678__image_banner`. Here they are `template--<template>__<key>` and `sections--<group>__<key>`, and blocks that come from a schema `default` get `block-1`, `block-2`…
- The `<!-- BEGIN sections: <group> -->` and `END` comments around a [section group](https://shopify.dev/docs/storefronts/themes/architecture/section-groups), which the page describes only as having "no markup between the sections"; the `shopify-section-group-<group>` class is shown by the [Section Rendering API](https://shopify.dev/docs/api/ajax/section-rendering) page's example response (which writes `className`, apparently a typo) and followed here.
- The `wrapper` grammar of a JSON template beyond the page's one example, and schema `tag` values beyond the documented six (any lowercase element name is accepted, and the 50-character limit on a block's `tag` is not enforced).
- A block's wrapper markup (`<div id="shopify-block-<id>" class="shopify-block">`), `class` when `tag` is `null` (not applied), and `block.shopify_attributes`, which is always empty because the package has no theme editor.
- `block.blocks` in a theme block: the children its `content_for 'blocks'` renders, listed as `section.blocks` lists a section's (static ones left out). The [`block` object](https://shopify.dev/docs/api/liquid/objects/block) page does not have it; Shopify's Horizon theme reads `block.blocks.size` in a theme block.
- Where a static section's saved settings live (`current.sections[<name>]` in [`settings_data.json`](https://shopify.dev/docs/storefronts/themes/architecture/config/settings-data-json), whose page documents only `current`, `presets` and `platform_customizations`), and `current` given as a preset name.
- A [static block](https://shopify.dev/docs/storefronts/themes/architecture/blocks/theme-blocks/static-blocks)'s saved entry sits under the `blocks` of the section or block it renders in, with `"static": true` and no place in `block_order`, as the page's "Static theme blocks in data" shows; this package requires the flag, and an entry without it is not used and is reported as `unsupported`. Still open: a saved entry whose `type` differs from the tag's (the tag's type wins), and `content_for 'block'` with no saved entry (the block renders with its schema defaults).
- The numbering of a [static block](https://shopify.dev/docs/storefronts/themes/architecture/blocks/theme-blocks/static-blocks) rendered again by the same section or block (`-1`, `-2`, also on the blocks inside it), which shopify.dev does not document: the count is per id within one render of the section or block that holds the tag, and a static block repeated inside a numbered one ends with both numbers (`heading-1`, then `heading-1-1`, inside `card-1`), which no recording shows.
- A request whose `view` and whose resource's `template_suffix` both name templates the theme has renders the view's: the [alternate templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/alternate-templates) page names both ways and not which wins, and no fixture holds both, so the order is Debutify's.
- Which template wins when a JSON and a Liquid template share a name (the JSON one), which wins in `renderSection` when a bare template key and a static section share a name, and group ids whose key contains `__`.
- The template renders before the layout, so a Liquid template's `assign` is not visible in its layout; the [layouts](https://shopify.dev/docs/storefronts/themes/architecture/layouts) page says Shopify can start sending the page when the layout reaches `content_for_header`, before the template's sections render.
- Contextual section groups: a `<group>.context.<context>.json` file applies when its `context` (`market` or `b2b`) matches the request's, and the storefront gives every page request the context of its market when the store data has that market (`context: { market }`, no `b2b`; a store with no markets has none), so the file named for the page's market handle overrides its parent group. [The page](https://shopify.dev/docs/storefronts/themes/architecture/section-groups#contextual-section-groups) does not say which file wins when several match (the first in file order here) or what happens when none does (the parent group as it is here), and a market handle the store data lacks (the private theme's `international` and its market-id files) never matches; how a file merges with its parent group (objects by key, arrays replaced) and `market` combined with `b2b` are Debutify's reading too.
- `renderSection` keeps the section's index on the page (the section object page says `section.index` is nil under the Section Rendering API), and accepts a section group's id, applying the request's `context`.
- The nesting limit of 100 for `section`, `sections` and `content_for` (`Nesting too deep`) is Debutify's number, taken from Ruby Liquid; a theme block that renders itself stops there, and `render` and `include` recursion runs to `renderLimit` instead.
- The exact text of `content_for_header` (shopify.dev says only that it holds all scripts Shopify requires), so a filter applied to it, such as `| size`, differs from a store.
- Malformed template fields are read as empty and reported (a saved block that is not an object is left out of `section.blocks`, and block `settings` that are not an object read as empty, both under the feature `blocks`), and the 25-section and 50-block limits of [JSON templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/json-templates) are not enforced.
- The section schema's `blocks` list (`@theme`, `@app`, block types) does not restrict what renders from saved data, and `disabled` on a block (documented for sections only) skips it.
- The text of a section's syntax error and of the `content_for` errors (unknown type, missing `type` or `id`), and where a failing block's error lands: a block file that does not parse is listed in `report.errors` with its file and line, but a block whose saved JSON or schema has the wrong shape prints an error such as `Liquid error: block <id>: "settings" must be an object` (`Liquid error: blocks/<type>.liquid: …` for its schema) in its own wrapper and is not listed in `report.errors`; its siblings and the rest of its section still render, and the section is reported as `failed` with that message as the `reason`.
- Block-level `t` lookups: a block resolves `sections.<section type>.<key>` through its section's schema `locales`.
- Where Shopify accepts a comment or a trailing comma in a theme JSON file: the [page](https://shopify.dev/docs/storefronts/themes/architecture#json-with-comments) says "Theme files with JSON support comments and trailing commas", shows a `//` comment after a value and a trailing comma in `settings_schema.json`, and lists the files whose comments Shopify does not persist (templates, section groups, `settings_data.json`, locale files). Here every such file accepts both anywhere outside a string, a comma counts as trailing only when it follows a value and precedes `}` or `]`, and a `//` comment ends at the line break; a byte order mark, single quotes and unquoted keys are not accepted.

## Storefront: `@debutify/liquidjs/storefront`

The `/storefront` entry serves a whole Shopify store from data. You give it a theme and a `StoreData` object, and it answers the requests a Shopify storefront answers, as a function from a standard `Request` to a standard `Response`: the pages, the [Cart Ajax API](https://shopify.dev/docs/api/ajax/reference/cart) and the cart forms, [section rendering](https://shopify.dev/docs/api/ajax/section-rendering), the product, predictive search and recommendations JSON, the contact, newsletter, localization and password forms, discount links, and the redirects between them. Every visitor has a cart, kept in a store you can replace. The pages and the Ajax answers come from the `/shopify` entry (see [Storefront requests](#storefront-requests)), which the storefront keeps external to its own bundle, so a process holds one copy of the engine.

It serves no files (theme assets, fonts and images are the host's, through the [`services`](#services) option), sends nothing (no email, no payment) and has no checkout or customer accounts: those addresses answer a [notice page](#the-notice-page). It is for Node.js 24 or newer, like `/shopify`: its `exports` entry has the same `types`, `module` and `default` conditions and no browser build. The engine's own gaps are under [Known gaps](#known-gaps); the storefront's are under [Known gaps of the storefront](#known-gaps-of-the-storefront).

### Serve a store

`createStorefront(options)` returns a `Storefront`, an object with one method, `handle(request, handleOptions?)`, which takes a `Request` and resolves to a `Response`. A bad request, a missing page and a failing render are all answers (a 400, a 404, a 500), not rejections; `handle` rejects when the host calls it wrongly (see `sandbox` below). Run this as an ES module on Node.js 24: it is a complete server for the mock.shop sample store.

```js
import { createServer } from 'node:http'
import { Readable } from 'node:stream'
import { createStorefront } from '@debutify/liquidjs/storefront'
import { storefrontSampleData } from '@debutify/liquidjs/shopify'

const theme = {
  files: {
    'layout/theme.liquid': '<!doctype html><html><head>{{ content_for_header }}</head><body>{{ content_for_layout }}</body></html>',
    'templates/index.json': '{ "sections": {}, "order": [] }',
    'templates/product.json': '{ "sections": { "main": { "type": "main-product" } }, "order": ["main"] }',
    'templates/cart.json': '{ "sections": {}, "order": [] }',
    'templates/404.json': '{ "sections": {}, "order": [] }',
    'sections/main-product.liquid': '<h1>{{ product.title }}</h1>{{ product.price | money }}',
    'sections/cart-count.liquid': '{{ cart.item_count }}'
  }
}

const storefront = createStorefront({ theme, data: storefrontSampleData })

createServer(async (req, res) => {
  const body = req.method === 'GET' || req.method === 'HEAD' ? undefined : Readable.toWeb(req)
  const request = new Request(`http://${req.headers.host}${req.url}`, { method: req.method, headers: req.headers, body, duplex: 'half' })
  const response = await storefront.handle(request)
  res.statusCode = response.status
  for (const [name, value] of response.headers) if (name !== 'set-cookie') res.setHeader(name, value)
  const cookies = response.headers.getSetCookie()
  if (cookies.length) res.setHeader('set-cookie', cookies)
  res.end(Buffer.from(await response.arrayBuffer()))
}).listen(3000)
```

`http://localhost:3000/products/hoodie` is now the hoodie's product page, and a cart change sets the visitor's cookie. Without a server, `handle` is called with a `Request` directly (with `storefront` from above):

```js
const add = await storefront.handle(new Request('https://shop.example/cart/add.js', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ id: 43695847538710, quantity: 2, sections: 'cart-count' })
}))
add.status // 200
add.headers.get('set-cookie') // 'cart=<32 hex digits>; Path=/; HttpOnly; SameSite=Lax'
const cookie = add.headers.get('set-cookie').split(';')[0]
const cart = await (await storefront.handle(new Request('https://shop.example/cart.js', { headers: { cookie } }))).json()
cart.item_count // 2
cart.total_price // 18000: two hoodies at 90.00
```

The request's own URL is the store's address: its host and origin print in the pages (`canonical_url`, the `hreflang` links, `request.origin`), so a host behind a proxy that rewrites the host builds the `Request` from the public address. Keep the same `theme` and `data` objects between requests, as `renderPage` asks: a theme object is compiled once and a `data` object has its views built once.

In a Next.js route handler the `Request` is the one Next gives, and `basePath` is the folder the route sits in. Next.js documents `route.ts` files that export a function per HTTP method, `GET`, `POST`, `HEAD` and the others, with `runtime = 'nodejs'` to pick the Node.js runtime ([Route Handlers](https://nextjs.org/docs/app/api-reference/file-conventions/route)); the storefront needs Node.js, not the Edge runtime.

```ts
// app/store/[[...path]]/route.ts
import { createStorefront } from '@debutify/liquidjs/storefront'
import { storefrontSampleData } from '@debutify/liquidjs/shopify'
import { theme } from '@/lib/theme' // a ThemeInput, see "Render a page"

export const runtime = 'nodejs'

const storefront = createStorefront({ theme, data: storefrontSampleData })

const handle = (request: Request) => storefront.handle(request, { basePath: '/store' })

export const GET = handle
export const HEAD = handle
export const POST = handle
```

The default cart store belongs to the storefront object, so carts live as long as that module instance does: a restart, or anything that evaluates the module again, starts with none, and a host that runs a separate instance per request keeps none. Pass a `cartStore` that outlives the process when carts must survive (see [Visitors and carts](#visitors-and-carts)).

### Storefront options

`createStorefront` takes a `StorefrontOptions` object. `theme` and `data` are required.

| Option | Default | Effect |
| --- | --- | --- |
| `theme` | required | The theme, a `ThemeInput` (`files`, optional `base`), or a function of the request that returns one, sync or async. A theme object is compiled once and kept by the engine, so a function must return the same object for the same theme: one that builds a new object on every request compiles the theme on every request. |
| `data` | required | The store, a `StoreData` object, or a function of the request that returns one. Pass the same object while the store is the same: its views are built once per object, and data edited in place keeps rendering the objects built before the edit. |
| `services` | `defaultServices` | A `Partial<ShopifyServices>` merged over the defaults for every render (see [Services](#services)), or a function of the request that returns one, called once per request like `theme` and `data`: a host that serves many base paths from one storefront uses it to put the base path into `assetUrl` and `fontUrl`. The defaults point at `/assets/<path>` and the like, which the storefront does not serve, so a host serves the files and sets the services to where it does. |
| `cartStore` | `memoryCartStore({ max: limits.visitors, idleMs: limits.idleMs })` | Where visitor states live, a `CartStore` (see [Visitors and carts](#visitors-and-carts)). |
| `notice` | the built-in page | `(kind, request) => Response \| Promise<Response>`, where `kind` is `'checkout'` or `'account'`: replaces the [notice page](#the-notice-page). |
| `limits` | `DEFAULT_LIMITS` | A `Partial<StorefrontLimits>` laid over the defaults; a limit given as `undefined` keeps its default. See [Limits and errors](#limits-and-errors). |
| `viewCacheSize` | 16 | The views of the store `data` kept, each a full copy of the store's objects for one base path, market and language: about 40 MB for 5,000 products and 45,000 variants, built in about 120 ms. A store served under many base paths (one per preview) builds one view per path; the least recently used is dropped past this number. A whole number of at least 1. See [the view cache](#storefront-requests). |
| `languages` | none | `'theme'`: publish the store in every language the theme has a storefront locale file for, besides the languages its data lists, each at its own subfolder (`/de`, `/pt-br`), in the primary market. See [Languages from the theme](#languages-from-the-theme). |
| `password` | none | The password `POST /password` accepts when the store data says the store is password protected (`shop.password_enabled`). With none set, no password opens a protected store. See [Password protection](#password-protection). |
| `onReport` | none | `(report, request) => void`, called with a `StorefrontReport` after every page or section render (`{ kind: 'render', report }`, the engine's [render report](#the-render-report)) and for every failure (`{ kind: 'error', error }`). A reporter that throws, or returns a promise that rejects, does not fail the request. |

Pages render in the engine's untrusted mode (see [Safety](#safety)) with its default `parseLimit`, `renderLimit` and `memoryLimit`: the storefront passes no trust option and no render limit, so a `liquid` setting prints as escaped text, and a render that runs past `renderLimit` is an error answer (a 500 page and an `error` report).

`handle(request, handleOptions?)` takes a `HandleOptions` object:

| Option | Default | Effect |
| --- | --- | --- |
| `basePath` | `''` | The path every storefront address starts with, such as `/p/<token>`. It is cleaned to one leading slash and no trailing or doubled one (`store/` is `/store`). An address outside it is the store's 404 page, and the base path is part of every link the pages print, of the redirects and of the visitor's cookie path. Give the storefront the whole request URL, base path included: it takes the base path off itself. |
| `visitor` | none | The visitor key, a non-empty string. When it is given, the `cart` cookie is neither read nor set and the visitor is this key. |
| `sandbox` | `false` | The page runs in a sandboxed iframe: cross-origin answers, no cookies, the client script in `<head>`. Needs `visitor`; `handle` rejects with a `TypeError` without it. See [Sandboxed pages](#sandboxed-pages). |

### Routes

Every address is read under the base path and an optional locale prefix (`/fr-ca/cart.js`; [Storefront requests](#storefront-requests) lists the prefixes a store serves). Every answer but a sandbox preflight and the files of [Shopify's global assets](#shopifys-global-assets) and a compiled file, the error pages included, carries `Cache-Control: private, no-store`, because it may hold or depend on one visitor's state. A `HEAD` request is answered like a `GET` with no body, and it changes nothing: a link checker that sends `HEAD` to `/discount/<code>` does not apply the code. A `GET` that a browser sends to prefetch or prerender a page (`Sec-Purpose: prefetch`, `Purpose: prefetch` or `X-Moz: prefetch`) changes nothing either: it is answered in full, the redirect of a discount link or of a remove link included, but no state is saved and no cookie is set, so a prefetched `url_to_remove` does not empty the line. A `POST` is never a prefetch.

The `.js` endpoints (`/cart.js`, `/cart/add.js`, `/cart/change.js`, `/cart/update.js`, `/cart/clear.js` and `/products/<handle>.js`) are `text/javascript; charset=utf-8`, their error answers included, except the "Cannot find variant" error of `add.js` and `update.js`, which is plain `application/json`. The `.json` endpoints (shipping rates, `/search/suggest.json`, `/recommendations/products.json`), the `?sections=` map and the empty 404 of an unknown product are `application/json; charset=utf-8`, and the empty 400 of a sixth section is `text/html; charset=utf-8`. A client should parse a JSON body whatever the type says.

### Shopify's global assets

`shopify_asset_url` names a file that Shopify hosts for every theme. On Shopify these are at hashed addresses under `/cdn/shopifycloud/storefront/assets/`, which cannot be known ahead of time, so the storefront answers `GET <base path>/shopify-assets/<path>` itself for the three files that the gift card templates of the private theme, Horizon and Dawn load. They are stand-ins by design, like [`placeholder_svg_tag`](https://shopify.dev/docs/api/liquid/filters/placeholder_svg_tag)'s art:

| Path | Type | What it is |
| --- | --- | --- |
| `vendor/qrcode.js` | `application/javascript; charset=utf-8` | `qrcode.min.js` of [davidshimjs/qrcodejs](https://github.com/davidshimjs/qrcodejs) at commit `04f46c6a0708418cb7b96fc563eacae0fbf77674`, byte for byte (sha-256 `c541ef06327885a8415bca8df6071e14189b4855336def4f36db54bde8484f36`), under its MIT licence with its notice (and Kazuhiko Arase's, which it holds) in the file's first comment and in `NOTICE.md`. The themes call `new QRCode(element, { text, width, height })`, which it provides. Not pinned: Shopify's copy takes an `imageAltText` option for the alt text of the image it draws; this library ignores it and its image says "Scan me!". |
| `gift-card/card.svg` | `image/svg+xml` | A neutral gift card drawn by Debutify, 570 by 380 as the themes' `<img>` is. Not Shopify's art. |

Every file is answered with `Cache-Control: public, max-age=604800` (the address holds no hash, so it is not `immutable`), an `ETag` (a request that holds it gets a 304), `X-Content-Type-Options: nosniff` and its length. A file is served at its exact address only, so each has one cached address: any other path, the bare `/shopify-assets/`, and a spelling that is not exactly the address (`vendor%2Fqrcode.js`, `//vendor/qrcode.js`, `vendor/qrcode.js/`) answer 404 with a plain body and `private, no-store`, a method other than `GET` and `HEAD` the 404 page. The route is read under the base path and the locale prefix, answers before the visitor's state is read, and is outside the storefront password, because the gift card page loads these files from its own sandbox. A host that sets its own `services.shopifyAssetUrl` serves the files itself.

### The cart

The Ajax endpoints read a JSON body, a url-encoded form or a multipart form, the three shapes themes post: `items[0][id]`, `properties[Engraving]` and `updates[<variant id>]` are read as nested fields, a file field is dropped, and a body may not be over `limits.body` bytes. A line is a variant with its properties and selling plan; a new line goes first, and an item that matches a line merges into it. All the items of one add are added or none is.

- `add.js` answers `{ "items": [...] }` when the request sent `items`, else the line.
- `change.js` takes `line` (1-based) or `id` (a line key, or a variant id as a string) and a `quantity` (0 removes the line), and `properties` or `selling_plan` to change them. It also lists the line that grew under `items_added` and the one that shrank under `items_removed`. A change that names no line, or an `id` that is not a string, is a 400.
- `update.js` takes `updates` (quantities by variant id, line key or position), `note`, `attributes` and `discount` (comma-separated codes that replace the cart's). It lists the variants that grew under `items_changelog.added`.
- `clear.js` empties the lines and keeps the note, attributes and discount codes.

A request may name `sections` (a comma-separated string or an array of up to `limits.sections` ids): the answer then holds them under `sections`, rendered after the change with the new cart, in the context of the page named by `sections_url` in the body, else by the `X-Storefront-Page` header, else by the path of the `Referer`, else `/`. More sections than the limit are not an error here: the change is made and `sections` is `null`. A cart error is Shopify's `{ status, message, description }`, almost always a 422 (a variant that does not exist or is sold out, more than the stock, a selling plan the variant lacks, a limit of this storefront), and nothing changes when one occurs.

The form spellings change the cart the same way and then redirect: to the `return_to` field (a path on the store, or `back` for the page the visitor came from), else `/cart`; a form with a `checkout` field goes to Shopify's checkout address (`/checkouts/cn/<cart token>/<language>-<country>?_r=…`), which shows the notice page. A cart error there is a plain page with Shopify's status, the description and a link back.

A `POST` to a spelling without an extension (`/cart/add`, `/cart/change`, `/cart/update`, `/cart/clear` and `/cart`) is answered as its `.js` endpoint is, in JSON and with no redirect, when the request asks for JSON: its `Accept` names `application/json`, `application/javascript`, `text/javascript` or a type ending in `+json`, or it has `X-Requested-With: XMLHttpRequest`. Dawn's product form posts `/cart/add` so (`Accept: application/javascript`, `X-Requested-With: XMLHttpRequest`) and reads the answer as JSON, and a theme's cart code posts `cart_change_url` and `cart_update_url` with `Accept: application/json`; a browser's form post asks for `text/html` and gets the redirect, and a `GET` is always the link. No shopify.dev page states this rule and no recording holds it: it is what those themes need.

Discounts are the store data's (`StoreData.discounts` and the codes in the cart). A discount applies to one-time purchases only: a line bought under a selling plan is not discounted unless the discount's flags say otherwise (`applies_on_subscription: true`; `applies_on_one_time_purchase: false` takes one-time purchases out). With the flags omitted they are `true` and `false`, as observed on the parity store, whose discounts were created without them. They are on every kind of discount, order and free shipping discounts included (the Admin API gives both to the `customerGets` of an order discount and to a free shipping discount, [`DiscountCustomerGetsInput`](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DiscountCustomerGetsInput) and [`DiscountCodeFreeShippingInput`](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DiscountCodeFreeShippingInput)): an order discount takes money off the lines of its purchase types, and its minimum is met by the purchase type's total before the product discounts and by the whole cart after them (the help centre's two checks); a free shipping discount needs a line of its purchase types, which its minimum counts. No recording covers a subscription under an order or a free shipping discount, and the parity store's own were not read for the default, so these follow the ruling for the other discounts.

### Redirects

Every redirect is a 302 with `Cache-Control: private, no-store`. A target that a visitor can write (`?redirect=` of a discount link, `return_to` of a cart form or of the localization form) must be a path on the store: one leading slash, not followed by another slash or a backslash, and no control character. Anything else (a host, `//host`, `/\host`, nothing) is replaced by the route's own default (`/` for a discount link and the localization form, `/cart` for a cart form), so a link cannot send a visitor to another site. A target is resolved the way a browser resolves an address before anything else is checked: `.` and `..` segments, in their percent-encoded forms (`%2e%2e`) and with backslashes for slashes, are applied, and cannot climb above the store's root, so `?redirect=/../../client/dashboard` is the store's `/client/dashboard`, never a path outside the base path. A target that hides a climb behind an encoded slash or backslash (`/..%2f..%2fclient`) is refused like a host, and so is one that resolves to `//host`. The same rule reads the page a form came from (`Referer`, `storefront_page`) and the page a cart answer's sections render in (`sections_url`, `X-Storefront-Page`). The base path is put in front of the target unless it already holds it (compared as the router compares segments, decoded), the request's locale prefix unless the target names a locale prefix of its own (`/fr-ca/…`), and characters outside ASCII are written as UTF-8 percent escapes, so `Location` is always a valid header.

### The notice page

Checkout and the customer account pages are Shopify's, not the storefront's. Their addresses (`/checkouts` and everything under it, `/customer_authentication` and everything under it, under the base path and a locale prefix; `/checkout` and `/account` redirect to them) answer, whatever the method, a plain page with status 200: "Available in your own store", a line saying that checkout or customer accounts work once the store is published on Shopify, and a link back to the page the visitor came from (the `Referer`, when it is a page inside the base path) or to the store's root. It loads no theme file. The `notice` option replaces it: `notice('checkout' | 'account', request)` returns the `Response`, whose status, headers and body are yours; the storefront sets `Cache-Control: private, no-store` on it.

### Password protection

When the store data says `shop.password_enabled`, a visitor who has not passed the password is sent to the password page: every address but `/password`, `POST /password`, the files of [Shopify's global assets](#shopifys-global-assets) and the page of a gift card the store holds is a 302 to `/password`, under the base path and the locale prefix, the JSON endpoints and a section asked of the password page (`?section_id=`, `?sections=`) included. The page itself is the theme's `password` template. `POST /password` with the `password` option's value redirects to `/` and marks the visitor as unlocked in their state; any other password renders the `password` template again with status 200 and `form.errors` holding `password: ['Incorrect password']`. The two passwords are compared as SHA-256 digests with `timingSafeEqual`, so the comparison takes the same time whatever their lengths.

The wrong-password text and its 200 status are Debutify's own: Shopify's password page was not recorded. The storefront has no rate limit on `POST /password`, or on any other route: a host that serves a store stand-alone must rate-limit it, or anyone can try passwords as fast as the storefront answers.

### Visitors and carts

Every request belongs to a visitor, and a visitor has a `VisitorState`, plain JSON that a `CartStore` keeps under the visitor's key:

```ts
interface VisitorState {
  cart: CartState // the /shopify entry's CartState: token, lines, note, attributes, discountCodes
  country?: string // the country and language chosen with POST /localization
  language?: string
  unlocked?: boolean // passed the storefront password
}

interface CartStore {
  get (visitor: string): Promise<VisitorState | undefined>
  set (visitor: string, state: VisitorState): Promise<void>
}
```

The key comes from one of two places. In cookie mode (the default) it is the `cart` cookie: a value of 16 to 128 letters, digits, `_` or `-`, anything else being ignored, and a request without one starts a new visitor with a key of 128 random bits (32 hex digits). The storefront sets the cookie on the first answer that changes the visitor's state (a cart change, a discount link, a locale choice, an unlocked password) when the request carried no valid one, as `cart=<key>; Path=<base path, or />; HttpOnly; SameSite=Lax`: no `Secure` attribute (a host serving HTTPS adds it to the header it sends) and no expiry, so it ends with the browser session, where Shopify's own `cart` cookie lasts two weeks. With the `visitor` option the key is the one the host passes, and no cookie is read or set.

`cart.token`, the cart's token in `/cart.js` and in the `cart` object of a page, is not always the key. The key is the visitor's only credential, and in cookie mode the cookie is `HttpOnly` so that no script on the page can read it; a token equal to the key would hand it to any script that reads `/cart.js`. So in cookie mode the token is a one-way derivation of the key, the first 32 hex digits of its SHA-256, and so it is with a `visitor` option and no `sandbox`. In `sandbox` mode the token is the visitor key the host passes, which is already in the page's address. A host that needs the session key uses the key it passes to `handle`, not the token.

`memoryCartStore(options?)` is the default store, exported so that a host can size it itself: `max` (visitors held, default 10,000), `maxBytes` (bytes of state held in all, default 256 MiB, counted as two bytes for each character of each state's JSON), `idleMs` (milliseconds of disuse after which a visitor is dropped, default 24 hours) and `now` (a clock, for tests); each size must be a whole number of at least zero, or it throws a `TypeError`. Reading and writing both count as use, and when the store is full, in visitors or in bytes, the least recently used visitor goes first; a state that alone is over `maxBytes` is not kept and evicts no one. It copies a state on the way in and on the way out, it lives in one process, and its carts are lost when the process restarts and are not shared between processes. `limits.visitors`, `limits.storeBytes` and `limits.idleMs` size only this default store; a `cartStore` you pass has its own limits. See [Limits and errors](#limits-and-errors) for what one visitor can cost.

In cookie mode a visitor costs a request: any request that changes state without a cookie (the cheapest is `GET /discount/<code>`, which has no body and answers a 302) stores a new visitor and sets a new cookie, so a flood of them evicts every real cart from the default store, whose capacity is `limits.visitors`. A host that serves cookie mode on the public internet rate-limits the storefront's routes in front of it, or passes a durable `cartStore` that keeps its own capacity and does not evict real carts for new ones. In `sandbox` mode the visitor is the host's token and nobody mints one.

Any object with `get` and `set` is a cart store. It must give back what `set` was given (`undefined` for a visitor it does not know), and it should drop idle visitors itself. A state it gives back that is not a `VisitorState` (no `cart`, no `cart.lines`, lines without a variant or a quantity, a note or attributes of the wrong type: what a schema change in a database can leave behind) is not trusted: the visitor starts with an empty cart that keeps the country, language and unlocked flag that are valid, the problem goes to `onReport` as an `error` (without the visitor's key), and the visitor's next change replaces the stored state. Routes that change a visitor's state (the cart endpoints and forms, discount links, `/storefront-storage`, `/contact`, `/localization` and `/password`) run one at a time per visitor, in the order they arrived, inside one `createStorefront`; reads run at once. That order is kept in memory: a store shared by several processes must protect itself against two writes for one visitor at the same moment, or the host sends one visitor's requests to one process.

```js
import { createStorefront, memoryCartStore } from '@debutify/liquidjs/storefront'
import { storefrontSampleData } from '@debutify/liquidjs/shopify'

// the default store, sized by hand: 500 visitors, an hour of disuse
const small = createStorefront({ theme, data: storefrontSampleData, cartStore: memoryCartStore({ max: 500, idleMs: 60 * 60 * 1000 }) })

// your own store: a Map stands in for a key-value service, and a state is plain JSON
const kv = new Map()
const cartStore = {
  async get (visitor) {
    const stored = kv.get(`cart:${visitor}`)
    return stored === undefined ? undefined : JSON.parse(stored)
  },
  async set (visitor, state) {
    kv.set(`cart:${visitor}`, JSON.stringify(state))
  }
}
const shared = createStorefront({ theme, data: storefrontSampleData, cartStore })
```

### Sandboxed pages

A preview that runs a theme you did not write must not let the theme's scripts reach the host that serves it. The storefront serves such a preview as a page in a sandboxed iframe under an address nobody can guess, `/p/<token>`, and `sandbox: true` is its half of that. The host's half is two things, and both are needed:

- Send `Content-Security-Policy: sandbox allow-scripts allow-forms` on every answer under the base path: pages, JSON, redirects, 404s and the host's own error answers, not only the pages the storefront returns. In `sandbox` mode the storefront puts that policy on each answer it returns that has no `Content-Security-Policy` of its own, as a second line of defence; it cannot reach the answers it does not return, so the host still sets it.
- Frame the page with `<iframe sandbox="allow-scripts allow-forms" src="/p/<token>/">`.

The reason is the origin. Under `sandbox` without `allow-same-origin`, a document has an opaque origin and not the host's, so the theme's scripts cannot reach the host's cookies, storage or pages; and the header keeps that true when the address is opened outside the iframe (a link opened in a new tab, a form post that navigates), which the iframe attribute alone does not. Never add `allow-same-origin`: the page would then have the host's origin and the sandbox would protect nothing. Scripts and forms are what a theme needs; modals, popups and navigating the parent page stay off. An opaque origin also has no working storage or cookies, which themes use, and its requests to the host are cross-origin and carry no cookies. So in `sandbox` mode the storefront answers for it, and the [client script](#the-client-script) gives the page in-memory storage and cookies.

```js
import { createStorefront } from '@debutify/liquidjs/storefront'
import { storefrontSampleData } from '@debutify/liquidjs/shopify'

const TOKEN = 'a-long-random-token-made-for-this-preview'
const BASE = `/p/${TOKEN}`
const SANDBOX = 'sandbox allow-scripts allow-forms'

const storefront = createStorefront({ theme, data: storefrontSampleData })

const sandboxed = (response) => {
  const headers = new Headers(response.headers)
  headers.set('content-security-policy', SANDBOX)
  return new Response(response.body, { status: response.status, statusText: response.statusText, headers })
}

/** The preview host: a fetch-style handler for the whole site. */
export async function host (request) {
  const { pathname } = new URL(request.url)
  if (pathname === '/') {
    return new Response(`<!doctype html><iframe sandbox="allow-scripts allow-forms" src="${BASE}/" style="border:0;width:100%;height:100vh"></iframe>`, { headers: { 'content-type': 'text/html; charset=utf-8' } })
  }
  if (pathname !== BASE && !pathname.startsWith(`${BASE}/`)) return new Response('Not found', { status: 404 })
  try {
    return sandboxed(await storefront.handle(request, { basePath: BASE, visitor: TOKEN, sandbox: true }))
  } catch {
    return sandboxed(new Response('Something went wrong', { status: 500 }))
  }
}
```

With `sandbox: true` (which needs `visitor`) the storefront changes six things:

- It answers a preflight (`OPTIONS`, for any address) at once with 204 and `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: content-type, accept, x-requested-with, x-storefront-page` and `Access-Control-Max-Age: 600`, before it reads anything. The host must hand `OPTIONS` requests under the base path to `handle`.
- Every other answer carries `Access-Control-Allow-Origin: *`: with an opaque origin, each request the page makes to its own host is cross-origin. No credentials are allowed, so this exposes nothing a direct request would not.
- The `Cookie` header is ignored and no `Set-Cookie` is sent: the visitor is the `visitor` option, whatever cookies the request carries.
- An HTML answer gets the client script first in its `<head>` (or, in a document with no `<head>`, after its `<html>` tag, else after its doctype; HTML with none of the three is not a page and is left alone). A section fragment, a redirect, a `HEAD` answer and JSON do not.
- `cart.token` is the visitor key.
- It reads `storefront_page` from the request's address as the page the visitor came from, before the `Referer`, which a sandboxed document does not send (see [The client script](#the-client-script)). It must be a path on the store, else it is ignored.

The token in the base path is the only key to the preview's cart: anyone who has the address can read and change it. Make it unguessable, one per preview, and send it nowhere else. A host that serves the theme's assets for such a page sends them with `Access-Control-Allow-Origin: *` too, because fonts, module scripts and `fetch` calls are cross-origin from an opaque origin.

### The client script

`storefrontClientScript({ basePath, storage? })` returns the script the storefront puts in a sandboxed page, as a string of plain ES5 that runs before any theme code. A host that never calls `handle` with `sandbox: true` has no use for it; one that builds its own pages puts it first in `<head>`:

```js
import { storefrontClientScript } from '@debutify/liquidjs/storefront'

const tag = `<script>${storefrontClientScript({ basePath: '/p/a-long-random-token' })}</script>`
```

The base path is the only value written into the script, as a JSON string with `<`, U+2028 and U+2029 escaped, so no base path can close the element. The script does six things:

- `localStorage` and `sessionStorage` become in-memory objects with the `Storage` methods (`getItem`, `setItem`, `removeItem`, `clear`, `key` and `length`). They start with `options.storage` (`{ local, session }`, two maps of text to text; empty without it) and, when it is given, a change is sent to `POST <base path>/storefront-storage` after 100 ms and when the page is hidden, which the storefront saves in the visitor's state for the next page; without `options.storage` they are gone when the page unloads. A property assigned by hand (`localStorage.key = value`) is not storage.
- `document.cookie` becomes an in-memory cookie jar. A cookie is removed by `max-age=0` (or negative) or an `expires` in 1970; no other expiry, `path` or `domain` is read.
- A root-relative address (`/cart/add.js`) given to `fetch`, `XMLHttpRequest`, a link (when it is clicked) or a form (when it is submitted) gets `Shopify.routes.root` put in front of it, which holds the base path and the locale prefix (the base path before the page has set it), unless it already starts with the prefix or the base path. An absolute URL or an address without a leading slash is the page's own to get right, as is a button's `formaction`, which is not read.
- On the store's own requests it sends the page's current path and query in `X-Storefront-Page`, which the storefront reads as the context for bundled sections (see [The cart](#the-cart)).
- A form posted to the store (`method="post"`, an address of the store's own) gets `storefront_page=<the page's path and query>` in its address when it is submitted, the old one replaced and before any fragment, because a sandboxed document sends no `Referer`. The storefront reads it as the page the visitor came from: where `return_to=back` goes, where the contact form's redirect goes, and the page a cart answer renders its sections in when nothing else names it. A button's `formaction` does not name the page, as it is not read either.
- It runs once per window: a second copy of the script does nothing, so what the page stored is kept and nothing is wrapped twice.

### Limits and errors

`DEFAULT_LIMITS` (frozen) holds the defaults of the limits that keep one request or one visitor from costing more than a host can bear. To change one, pass it in the `limits` option.

| Limit | Default | Applies to |
| --- | --- | --- |
| `body` | 65,536 | Bytes of a request body, checked against `Content-Length` first and again as the body is read. |
| `lines` | 100 | Lines in a cart, items in one `add.js` and entries in one `updates`. |
| `quantity` | 9,999 | Units on one line. |
| `properties` | 25 | Properties of one line, attributes of a cart and discount codes of a cart (the oldest code goes first when a discount link adds one more). |
| `propertyLength` | 255 | Characters in a property name or value, an attribute name, a discount code and a shipping address part. |
| `noteLength` | 5,000 | Characters in the cart note. |
| `attributeLength` | 1,000 | Characters in the value of a cart attribute. |
| `sections` | 5 | Sections in one `?sections=` or one cart answer. |
| `search` | 256 | Characters in a search term (`q`), on every route that reads one: pages, sections, the vendor and type lists and predictive search. |
| `visitors` | 10,000 | Visitors the default cart store holds. |
| `idleMs` | 86,400,000 | Milliseconds of disuse after which the default cart store drops a visitor. |
| `storeBytes` | 268,435,456 (256 MiB) | Bytes the default cart store may hold in all; past it the least recently used visitors go. |

Every limit given must be a whole number of at least zero: `createStorefront` throws a `TypeError` that names the limit for `NaN`, a negative number, a fraction, infinity or anything that is not a number, where a body limit of `NaN` would otherwise build and make every `POST` a 500. To lift a limit, pass `Number.MAX_SAFE_INTEGER`. No shopify.dev page or recording states a length for the cart note or for an attribute's value, so `noteLength` and `attributeLength` are Debutify's (the note's 5,000 is the figure Dawn merchants report for Shopify's note, undocumented); a longer one is a 422 with `The cart note can be at most 5000 characters.` or `A cart attribute value can be at most 1000 characters.`, and nothing changes.

**What one visitor can cost.** Under the default limits a visitor's state is at most about 1.34 MB as JSON (measured: 100 lines each with 25 properties of 255 + 255 characters, a full note, 25 full attributes and 25 full discount codes). The default cart store counts two bytes for each character of a state's JSON, so that is 2.68 MB counted, and `storeBytes` bounds the store: with the default 256 MiB the states it holds are at most 268,435,456 counted bytes (about 128 MiB of JSON, some 100 visitors with carts full to the limit, or the whole 10,000 visitors for carts up to about 13 KB), and the least recently used visitors go when a state would push it over. The count is of the states only: each visitor also costs a few hundred bytes of object overhead, so the process holds a small multiple of the figure for a store full of tiny carts. A state that alone is over `storeBytes` is not kept. Hosts that set `limits` higher raise these figures in proportion; a host that passes its own `cartStore` bounds it itself.

Fixed limits of the engine, which `limits` does not change: a collection or search address is read for its first 100 query pairs, of which the first 25 `filter.*` parameters and the first 50 values of each count as filters. The rest of its query is ignored: it filters nothing and is not repeated in the filter and page links. The work of a request grows with the filters it names (each value is tested against every product) and with the pairs its links repeat, and shopify.dev gives no limit, so these are Debutify's. A page that names more shows the products and links of the first ones: with 60 `filter.p.vendor` values, the first 50 filter.

What the storefront answers when something is wrong:

| Situation | Answer |
| --- | --- |
| A body over `limits.body` | 413 with `{ "status": 413, "message": "Payload Too Large", "description": "…" }`. |
| A body that cannot be read or parsed: bad JSON, JSON that is not an object, a form that is not valid, one field used both as a value and as a group (`a=1&a[b]=2`) | 400 with `{ "status": 400, "message": "Bad Request", "description": "…" }`. |
| A cart change that is wrong or over a limit | A Cart API error, `{ status, message, description }`, almost always 422; the description names the limit (`The quantity must be a whole number from 1 to 9999.`). Nothing changes. On a cart form, a plain page with the same status. |
| More than `limits.sections` ids in `?sections=` | 400 with an empty body. In a cart answer, the change is made and `sections` is `null`. |
| A section that is missing or fails | 404 with an empty body for `?section_id=`; `null` under its id for `?sections=` and in a cart answer. |
| A page whose resource is missing, or an address the store does not serve | The theme's `404` template with status 404; a plain page when the theme has none or it fails. |
| A render, the theme or data function, or the cart store throws (a JSON file of the theme that does not parse, such as `config/settings_data.json` or `templates/index.json`; a render over `renderLimit`). A Liquid syntax error is not one: the page is answered with status 200 and the engine's inline `Liquid syntax error (…)` text, as `renderPage` prints it, and `onReport` gets the render report with the error | 500, a plain "Something went wrong" page with no detail, and `onReport` gets `{ kind: 'error', error }`. |
| `handle` with `sandbox: true` and no `visitor` | `handle` rejects with a `TypeError`: it is the host's bug. |

### Languages from the theme

A Shopify theme ships a storefront locale file for each language it translates (`locales/de.json`, `locales/pt-BR.json`, next to its one `*.default.json`), and a merchant publishes the languages they want. A store built from data has no merchant, so `languages: 'theme'` publishes the theme's languages: the store is offered in every language the theme has a file for, which is what a preview needs to show a theme in all its languages. Horizon 4.3.0 ships 34, Dawn 16.0.0 ships 31, and the private theme ships its default only (so the option changes nothing for it).

- **The pages.** Each language is at `<base path>/<language in lower case>`: `/de`, `/pt-br`, `/zh-tw`, `/ar`. Its pages read its locale file for `t`, with plural keys by the language's CLDR categories (`Intl.PluralRules`: `zero`, `one`, `two`, `few`, `many`, `other`), a key the file lacks from the base language (`pt-BR` then `pt`) and then the default file, and the schema locale files the same way for `t:` defaults. Content with no translation in the language (`StoreData.translations`) shows the primary language's text, as [Shopify's help centre](https://help.shopify.com/en/manual/international/languages) says. `request.locale`, `localization.language` and `localization.available_languages` describe it (`iso_code` as the file names it, `name` in the page's language (shopify.dev says the primary locale; the recording `flow-localization-language` shows `français` on a French page, which the parity store's behaviour here follows), `endonym_name`, `primary`, `direction`, `root_url`); Arabic, Hebrew and Urdu are `rtl`, which Horizon reads for `<html dir>`.
- **Switching.** `POST /localization` with `language_code` (or `locale_code`) goes to the language's root or to `return_to` under its subfolder, and back to the unprefixed primary language; links on a page keep its subfolder (`routes.*` and every resource `url`).
- **Not pinned.** shopify.dev gives no subfolder rule for a regional language: the help centre writes `/de`, `/en-ca` and `/es-mx` in lower case and does not show `pt-BR`, so lower case is Debutify's. It does not say whether a market other than the primary one offers the theme's languages (here none does: that would put a subfolder and an `hreflang` tag per country and language on every market). Shopify's names for the Chinese scripts and Norwegian are the help centre's list (`Chinese (Simplified)`, `Chinese (Traditional)`, `Norwegian (Bokmål)`); the other names and endonyms are the runtime's `Intl.DisplayNames`, which differ from Shopify's in letter case and wording for some languages. The `date` and `time_tag` defaults follow the page's language, as the locale files page says ("default format options that will display in the appropriate format for the store's active language"): for a language other than English the named formats (`abbreviated_date`, `basic`, `date`, `date_at_time`, `default`, `on_date`, `short`, `long`) are written by `Intl.DateTimeFormat` for it, and `%A %a %B %b` print the language's day and month names; English keeps its strings, which the parity recordings pin. Not pinned: what each named format prints in each language (the order of the parts, the punctuation and the digits come from the runtime's CLDR data, Arabic in Arabic-Indic digits; `on_date` has no preposition, and `default` no zone, outside English), and whether Shopify translates the names under a raw `%B` (the page shows only `date_formats` keys). A theme's `date_formats` key is read from the active language's locale file (its own, then its base language's) and never from the default file's, where the page says a missing format "is a Liquid error": a page in German whose `de.json` lacks the key prints the engine's error.

### Storefront public API

From 1.1.0, the release that adds the entry, semver covers what `@debutify/liquidjs/storefront` exports, and nothing else: the functions `createStorefront`, `memoryCartStore` and `storefrontClientScript`, the value `DEFAULT_LIMITS`, and the types `StorefrontOptions`, `HandleOptions`, `Storefront`, `StorefrontLimits`, `StorefrontReport`, `CartStore` and `VisitorState`. Anything imported from a deeper path (`@debutify/liquidjs/dist/...`) is not covered.

### Known gaps of the storefront

The storefront is compared with Debutify's parity store request by request. These differences are kept on purpose, each with its reason, and none hides another difference in the same scenario or page.

Steps accepted by a rule that names the answer standing in for Shopify's (every other step of the scenario is still compared):

- `contact-bot-challenge` (scenarios `flow-contact-*`): Shopify's bot challenge answers scripted contact posts with 403, so no recording holds Shopify's answer to a post.
- `customer-accounts` (scenarios `ajax-checkout-redirects` and `flow-checkout`): the customer accounts are Shopify's own site (`https://shopify.com/<shop id>/account`), which a sandboxed preview cannot follow: the storefront answers `/account` with a 302 to `/customer_authentication/redirect` carrying the same language and country, and answers that address with the notice page.
- `atom-feeds` (scenario `ajax-endpoint-links`): the Atom feeds `content_for_header` links (`/collections/<handle>.atom`, `/blogs/<handle>.atom`) write each product under the id Shopify's store gave it (`products/15428064215339`) and with the time the store last changed it, which the dataset holds neither of, so the storefront does not serve them; the oEmbed answers are compared in full.
- `cart-link-gone-page` (scenario `ajax-checkout-redirects`): a cart permalink to a variant the store lacks answers 410 with Shopify's error page (its own artwork, a request id that changes every time); the storefront answers 410 with a page that says the same.

Redirect addresses with their opaque values masked on both sides (scenarios `ajax-checkout-redirects`, `ajax-cart-form-add` and `flow-checkout`): `checkout-address-values` hides the cart token, the signature `_r` and the permalink's `cart_link_id`, which Shopify makes itself; the language, the country and the other parameters are compared.

Parts of scenarios that are accepted (only the named snippet or key is replaced by one fixed text on both sides, so every other difference still shows):

- `customer-account-login-address` (scenarios `page-*`, `probe-page-*` and `flow-localization-*`): customer accounts are not served, since the storefront has none: Shopify's login address is its own customer-authentication redirect, the storefront's is its notice page at /account/login.
- `accelerated-checkout-store-values` (scenarios `page-product*`): Shopify prints the shop's own storefront access token, shop id and wallet flags in `<shopify-accelerated-checkout>`; the storefront prints a stable token and id of the same shape, made from the store's domain. The buyer's country, language and currency, the variants and the element's content are compared.
- `placeholder-art` (scenarios `page-*`): placeholder_svg_tag draws Shopify's own artwork, which cannot be copied; the engine draws its own, so only the tag and its classes are compared.
- `search-ranking` (scenarios `probe-search-shirt` and `probe-search-type-product`): Shopify's search relevance orders the results its own way; the results themselves (which products and articles) are still compared.
- `search-article-order` (scenario `page-search`): Shopify's search relevance orders the matching articles its own way (liquidpeak-450 before new-line-of-tennis-products); the articles on the page and each card are still compared.
- `predictive-search-matches` (scenario `probe-predictive-prefix`): Shopify's predictive search matches a prefix such as `ca` against more fields than the engine does (it returns the hoodie), which is its relevance and not data.
- `recommended-products` (scenario `probe-recommendations-related`): Shopify samples related products from the store's sales, which this store never had, so the products it lists are its own pick; their count is still compared.
- `shipping-markup` (scenarios `ajax-shipping-rates-en-ca` and `ajax-shipping-rates-en-eu`): Shopify prints the markup of a shipping rate in another currency as the printed price less the base rate at its live exchange rate (CAD -0.17, EUR 1.15), which the dataset does not hold and which changes daily; the storefront prints 0.00. Every other field of those rates, the converted price included, is still compared.
- `recommended-products-json` (scenario `ajax-recommendations-json`): Shopify samples the related products of the recommendations answer at random (pr_seq=uniform, pr_prod_strat=collection_fallback) and puts a random pr_rec_id in each product url; the answer's intent and the number of products are still compared.

Probe keys that the engine cannot match, accepted in `test/storefront/all-probes.spec.ts`. The recorded value is left out (or, for `results`, compared as a set) and the value the engine prints is pinned instead, so a change to it still fails:

- `results` of `probe-search-shirt` and `probe-search-type-product`: Shopify ranks search results by its own relevance, which the dataset does not carry and no rule of plain matching reproduces (the engine lists them in store order); the results are compared as a set, and the engine's order is pinned.
- `products` of `probe-predictive-prefix`: for `q=ca` Shopify's predictive index finds the `hoodie` before `canvas-sneakers`, though nothing in the dataset for the hoodie holds a word that starts "ca"; the engine finds `canvas-sneakers` alone.
- `products` of `probe-recommendations-related`: Shopify samples related products per request from its own recommendation model (two recordings of one request share two of four products); the engine lists the products of the product's collections, then of its type, in store order.
- `routes.account_login_url` of `probe-page-home`, `probe-page-en-ca`, `probe-page-en-eu`, `probe-page-fr-ca` and `probe-page-fr-eu`: the parity store uses new customer accounts, whose login address is Shopify's `customer_authentication/redirect` on the store's myshopify domain, a setting the dataset does not carry; customer accounts are out of the item's scope, so the engine prints the classic `<prefix>/account/login`.

What no recording or shopify.dev page pins is Debutify's own choice, and may differ from Shopify:

- The password page: the wrong-password text, its 200 status, and every other address redirecting to `/password` until the visitor has passed it.
- The gift card page: an unknown card, a store with no card and a card with no `url` answering the theme's `404` template with status 404 (shopify.dev says nothing of them), a disabled or expired card being shown (the themes print their own notice from `gift_card.enabled` and `gift_card.expired`), and the card's `url` being served on the storefront's own host where Shopify hosts it on `checkout.shopify.com`. The gift card page bypassing the storefront password follows shopify.dev's statement that Shopify hosts the page on its checkout domain, and the password page was not recorded; a card's `template_suffix` choosing `gift_card.<suffix>` is the property's description ("the name of the custom template assigned to the gift card") read with the alternate templates page's naming, which the gift card template page does not repeat. The parity store holds no gift card, so no recording covers the page.
- The contact and newsletter forms send nothing, and their error wording (`can't be blank`, `is invalid`) is the storefront's.
- A cart add for more units than the stock holds adds nothing and answers 422, where shopify.dev says Shopify adds the maximum; the text for one unit left is the storefront's. The `.json` spellings of the cart endpoints are undocumented and are the same endpoints as the `.js` ones.
- The `cart` cookie ends with the browser session, where Shopify's lasts two weeks.
- The Ajax answers (`/cart.js`, `/cart/add.js`, `/products/<handle>.js`, …) write a whole decimal (`total_weight`, `presentment_price`, `aspect_ratio`, a selling plan's `checkout_charge.value`) as a plain number (`600`), where Shopify writes `600.0`; the JSON value is the same, and the comparison reads these answers as JSON. `{{ cart | json }}` and the Liquid objects print the point.
- The limits in the table above are the storefront's own; Shopify's differ.
- A section asked for at `/variants/<id>/?section_id=…`: the parity store answered `pickup-availability` (a store with no pickup location) with 200 and the empty wrapper, and a variant it lacks with 404 and an empty body (one `section_id` request each, no fixture; the `sections=` answer for an unknown variant is taken to be the same and was not observed). The template the section sees (`template`, `request.page_type`) is the 404 page's here, which shopify.dev does not pin; `product` is not set, as [the pickup availability guide](https://shopify.dev/docs/storefronts/themes/delivery-fulfillment/pickup-availability) says; and `product_variant.store_availabilities` is nil, because the store data has no locations, so the guide's `| where: 'pick_up_enabled', true` gives an empty list. A theme without a `404` template cannot answer the request.

Files are the host's, not the storefront's:

- `font_url`, and the `src` of the rule `font_face` writes, point at `/fonts/<directory>/<file>` (the default `fontUrl` service), a path the storefront does not serve: a host must serve the font files there (`https://fonts.shopifycdn.com/<directory>/<file>` has them, and `isShopifyFontFile` says which paths are the library's, so a host that proxies them fetches nothing else), or set `services.fontUrl` to where it does. The preview host does not serve them yet, so a page that loads a theme font gets a 404 for each file.
